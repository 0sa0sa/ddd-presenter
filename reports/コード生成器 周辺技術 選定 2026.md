# 生成器を一次情報に据え、道具には検証を任せる

結論から言うと、2026 年 10 月時点の DDD Presenter に足す道具は「生成器が型と契約の唯一の正を持ち続け、外部の道具には差分・検証・転送だけを任せる」という一本の原則で選べる。**DB** は、生成器が DDL・クエリ・型付きアクセスコードを出し続ける。sqlc には置き換えず、CI でクエリを検証する役にとどめる。マイグレーションは宣言的差分ツール **psqldef（v3.11.19 以上）** に任せる。Atlas は RLS と拡張が有償の Pro 限定なので次点、pgroll は大きなテーブルの破壊的変更に限って使う。**メッセージング** は、ブローカーに依存しない Port を出す。その下に Postgres のアウトボックスとポーリング中継、CloudEvents 1.0 のエンベロープ、受信側の冪等化（inbox）を置き、最初のアダプタは SQS（標準キュー + fair queues、順序が要るものだけ FIFO）にする。Kafka は再生や長期保持が要るときのオプションにする。**API** は gRPC ではなく **OpenAPI 3.1** にする。既存の Zod 契約と自前の TanStack Query ファクトリはそのまま残し、OpenAPI はそこから派生させる。互換性は oasdiff で検査し、ConnectRPC は社内のサービス間通信に限った条件付きのオプションにする。**OpenTelemetry** については、「トレースを抽象化したい」という要望にはあえて逆らう。自前の Tracer ポートは作らず、生成コードが OTel API を直接呼ぶ形を勧める。OTel 公式が「生成コードから直接呼ぶ」形を正当な例外として名指ししており、API は SDK がなければ no-op になるからだ。ドメインを純粋に保つ目的は、層の分け方で満たせる。**テスト** は、DSL の制約から Hypothesis / fast-check の strategy と状態機械テストを直接生成するのが最も費用対効果が高い。契約テストは OpenAPI を出したあとの Schemathesis だけで足り、Pact と実行する BDD は採らない。**取り入れる順番** は依存関係で決まる。DB の差分の流れとプロパティベーステストを先に入れ、次に OTel、続いて OpenAPI、その次にアウトボックスと受信側を入れる。状態機械テスト、実行しない `.feature` ドキュメント、条件付きの Connect はその後に続く。

## psqldef が差分を担い、sqlc は検証器に退く

生成器はすでに型付きのリポジトリとリーダーを TS（node-postgres / PGlite）と Python（psycopg 3 の同期接続）向けに出している。なので問題は「sqlc に置き換えるか」ではなく「sqlc を何に使うか」になる。sqlc 本体は活発で、2026-04 に v1.31.1 が出ており、PostgreSQL 向けにはデータベースだけで解析する実験的なアナライザも入った ([sqlc releases](https://github.com/sqlc-dev/sqlc/releases))。一方、公式の言語プラグインは止まっている。**sqlc-gen-python は 2025-01 の v1.3.0 で止まり**、2026-01 に「Maintained?」という issue が立ったが返答がない ([issue #94](https://github.com/sqlc-dev/sqlc-gen-python/issues/94))。しかも生成されるコードは psycopg ではなく SQLAlchemy に依存する ([gen.go](https://github.com/sqlc-dev/sqlc-gen-python/blob/main/internal/gen.go))。**sqlc-gen-typescript は README で "early access" を自称し、最新リリースは 2024-01 の v0.1.3**、LICENSE ファイルもない ([sqlc-gen-typescript](https://github.com/sqlc-dev/sqlc-gen-typescript), [issue #52](https://github.com/sqlc-dev/sqlc-gen-typescript/issues/52))。キーセットのページングで使う行値比較 `(a, b) < ($1, $2)` には、2 つ目のパラメータに誤った型が付く既知の不具合があり、修正しない扱いで閉じられている ([issue #1549](https://github.com/sqlc-dev/sqlc/issues/1549))。`SET LOCAL` も構文エラーになる ([issue #4186](https://github.com/sqlc-dev/sqlc/issues/4186))。生成器は DSL から型を正確に知っているので、型推論を sqlc にやらせ直すと、型の一次情報が DSL と sqlc の推論結果の二つに割れるだけだ。sqlc に残る正当な役割は、生成された SQL を使い捨ての DB に PREPARE して検証する `sqlc vet` の `sqlc/db-prepare` ルールくらいだ ([managed databases](https://docs.sqlc.dev/en/latest/howto/managed-databases.html))。それも、生成器がパラメータに `$n::type` を常に付ける前提でのことになる。

マイグレーションの側では psqldef が最もよく合う。望ましいスキーマを素の SQL で受け取って差分 DDL を出し、**DROP は既定でスキップ**する。`--check` は適用すべき DDL があると終了コード 2 を返すので、CI でドリフトを検出する門としてそのまま使える。対応範囲も広く、`ENABLE` / `FORCE ROW LEVEL SECURITY`、`CREATE POLICY`、拡張、演算子クラス付きのインデックス、CONCURRENTLY を扱える ([cmd-psqldef.md](https://github.com/sqldef/sqldef/blob/master/cmd-psqldef.md))。生成器が出す `USING gin (lower(email_value) gin_trgm_ops)` のような式インデックスの opclass への対応は **2026-07 の v3.11.18 で入り、opclass の変更検出は v3.11.19 で入った**。それより古い版は使わないこと ([sqldef releases](https://github.com/sqldef/sqldef/releases))。注意点が二つある。一つは、拡張を既定で「DB 内の全部」管理するので、`manage.extension` で pg_trgm だけに絞ること。もう一つは、ライセンスがパーサ部分だけ MIT と別扱いになっていることだ ([LICENSE](https://github.com/sqldef/sqldef/blob/master/LICENSE))。

比べた結果、他の候補はそれぞれ理由があって外れる。Atlas は宣言的・versioned の両方に対応し、ロックの危険を分類する lint も強い。しかし **RLS ポリシー、拡張、ドリフト検出、PG のロック系 lint（PG1xx / PG3xx）は Pro（月 9 ドル・席）限定**で、Apache-2.0 の Community Edition は RLS も拡張も扱えない ([Atlas features](https://atlasgo.io/features), [community edition](https://atlasgo.io/community-edition), [lint analyzers](https://atlasgo.io/lint/analyzers))。この生成器の DDL を扱うなら実質 Pro が前提になる。無償版にポリシー入りの SQL を渡すと、ポリシーが黙って落ちるのかエラーになるのかは確認できていない。テナント分離にとっては、確かめずに使えない点だ。Drizzle と SQLAlchemy + Alembic は、スキーマの一次情報を ORM のコードに置く設計なので、生成器が DDL を持つ方針とぶつかる。Drizzle は FORCE RLS をドキュメントに書いていない ([Drizzle RLS](https://orm.drizzle.team/docs/rls))。Alembic の autogenerate はリネームを drop + add と誤検出し、CHECK 式の変更も検出しない ([Alembic autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html))。Kysely の型生成は稼働中の DB を読む方式で、型をすでに持つ生成器にとっては冗長になる ([Kysely generating types](https://kysely.dev/docs/generating-types))。PostgreSQL 専用の pgschema（Apache-2.0、FORCE RLS と CONCURRENTLY に対応。README の対応オブジェクト一覧に拡張は載っていない）は psqldef の有力な次点になる ([pgschema](https://github.com/pgplex/pgschema))。docs/05 が差分ツールとして挙げている migra は**リポジトリ自身が DEPRECATED と書いている**ので、記述を差し替えるべきだ ([migra](https://github.com/djrobstep/migra))。ゼロダウンタイムの expand / contract は pgroll（v0.16.3、Apache-2.0）が無難だ。reshape はリリースが再開したものの、継続性が読みにくい ([reshape](https://github.com/fabianlindfors/reshape))。ただし pgroll のバージョン付きビューが下のテーブルの RLS を尊重するのは、`security_invoker` を使える **PG 15 以上だけ**だ ([execute.go](https://github.com/xataio/pgroll/blob/main/pkg/roll/execute.go))。Liquibase は FSL ライセンスに移っている ([LICENSE.txt](https://github.com/liquibase/liquibase/blob/master/LICENSE.txt))。

では「生成器が SQL を出し、型付きアクセスとマイグレーションを道具に分担する」という形は成り立つか。答えは条件付きで成り立つ、だ。ただし分担の中身は問いの想定と少し違う。型付きアクセスは道具に渡さず、生成器が持ち続ける。道具に渡すのはマイグレーションと検証になる。そしてこの分担には、確かめていない前提が一つある。今の出力は `CREATE … IF NOT EXISTS` と `DROP POLICY IF EXISTS` → `CREATE POLICY` を並べた冪等な bootstrap だ。これは「状態」ではなく「手続き」を含んでいるので、psqldef がそれを望ましいスキーマとして受け付けるかは、ドキュメントからは判断できなかった。したがって最初の作業は二つになる。生成器に、差分ツール向けの**純粋な状態の DDL を出すモード**を足すこと。そして cleaning-platform の例で「apply → 再 plan で差分ゼロ」の往復を実際に確かめることだ。今の冪等な bootstrap は、PGlite のテストと新しい DB の初期化用として残せばよい。運用上の最大の落とし穴は FORCE RLS にある。PostgreSQL ではテーブル所有者も FORCE で RLS の対象になり、スーパーユーザーと BYPASSRLS を持つロールは常に素通りする ([PostgreSQL Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html))。このため、データ移行や pgroll の backfill をテナント設定なしの所有者ロールで流すと、0 行しか対象にならない。マイグレーション専用の BYPASSRLS ロールを最初から設計に入れておくべきだ。インデックスについても、非 CONCURRENT の作成は書き込みを止める。CONCURRENTLY はトランザクションに入れられず、失敗すると INVALID なインデックスが残る ([CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html))。インデックスの追加は、他の変更とは別のデプロイ段階に分けるのが安全だ。

## アウトボックスと冪等な受信が、ブローカー選びより先に来る

メッセージングで生成器が保証できるのは、どのブローカーを選んでも「**at-least-once の配送 + 冪等なコンシューマ + aggregate の中だけの順序**」に尽きる。アウトボックスの中継は、送信したあと「送信済み」と記録する前に落ちると同じメッセージを再送するので、受け手は冪等でなければならない ([microservices.io](https://microservices.io/patterns/data/transactional-outbox.html))。ブローカー側の重複排除はどれも時間窓が短い。SQS FIFO は 5 分 ([AWS: exactly-once processing](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html))、NATS JetStream は既定で 2 分だ ([NATS docs](https://docs.nats.io/jetstream/model_deep_dive))。Kafka のトランザクションは Kafka の中の read-process-write を閉じるだけで、DB への書き込みを exactly-once にはしない ([Conduktor](https://conduktor.io/blog/exactly-once-semantics-when-it-works))。Pub/Sub の exactly-once も、同一リージョンの pull 購読に限られ、publish 側の重複は防がない ([Google Cloud: exactly-once](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery))。だから生成器は、どの基盤を使っても inbox を省けない。そして「exactly-once」とは名乗らないこと。

アウトボックスの既定は、CDC ではなく**ポーリング中継**にする。理由は三つある。Debezium Server の sink 一覧には Kinesis・Pub/Sub・NATS JetStream などは並ぶが、**SQS / SNS の sink がない** ([Debezium Server](https://debezium.io/documentation/reference/stable/operations/debezium-server.html))。生成器のテストが回る PGlite には WAL もレプリケーションスロットもない。そして CDC は JVM と論理レプリケーションの運用を求める。ただしテーブルの列は Debezium Outbox Event Router の既定（`id, aggregatetype, aggregateid, type, payload`）と互換にしておく。そうすれば、Kafka を使う段になって CDC に移れる。Router は `aggregateid` をメッセージのキーにするので、生成器の順序の方針ともそのまま合う ([Debezium Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html))。ポーリングには順序の罠が二つある。一つは、シーケンスの ID が採番の順であってコミットの順ではないことだ。カーソルで追う中継は、後からコミットされた若い ID を永久に取りこぼす ([cloudscale.ch](https://www.cloudscale.ch/en/engineering-blog/2025/10/09/generating-truly-sequential-ids-in-postgresql))。対策は、各行に `xid8` のトランザクション ID を記録し、`pg_snapshot_xmin(pg_current_snapshot())` より小さい行だけを配ることだ ([event-driven.io](https://event-driven.io/en/ordering_in_postgres_outbox/))。その代わり、長く開いたトランザクションが一つあるだけで配信が遅れるので、`idle_in_transaction_session_timeout` と中継の遅延の監視を組にする必要がある。もう一つの罠は、`FOR UPDATE SKIP LOCKED` だけで中継を並列にすると、同じキーの新しい行が古い行を追い越すことだ ([PR #3](https://github.com/AlexGorbatov/order-payment-platform/pull/3))。並列にするなら、aggregate のハッシュでシャードするか、aggregate 単位の advisory lock を取る。このプロジェクトに特有の衝突もある。アウトボックスに org_id の RLS をかけると、全テナントを横断して読む中継は行を見られない。中継には、アウトボックスに限った専用ロールか、中継用のポリシーが要る。

順序のキーは、Kafka のキーでも SQS / SNS FIFO の `MessageGroupId` でも Pub/Sub の ordering key でも、**aggregate ID にすべきで、テナント ID にしてはいけない**。SQS FIFO は MessageGroupId をハッシュしてパーティションに振り分け、多様な値を推奨している。1 パーティションは send / receive / delete それぞれ 300 msg/s が上限だ ([AWS: high throughput FIFO](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/high-throughput-fifo.html))。SNS FIFO は message group あたり 300 msg/s が上限で、東京リージョンのアカウント既定は FIFO で 3,000 msg/s だ ([AWS: SNS quotas](https://docs.aws.amazon.com/general/latest/gr/sns.html))。テナントをキーにすると、ホットテナントが一本の直列の列になる。しかも 1 件の失敗でテナント全体が止まる。テナントをまたぐ noisy neighbor 対策には、2025-07 に入った **SQS fair queues** が効く。標準キューに MessageGroupId（= テナント）を付けるだけで、偏ったテナントより他のテナントの配信が優先される ([AWS: fair queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-fair-queues.html))。これは FIFO の「MessageGroupId = aggregate」とは同じキューで両立しない。そこで、policy ごとに DSL で `ordered` を宣言させ、順序が要るものは FIFO に、それ以外は標準キュー + fair queues に振り分けるのが素直な設計になる。SNS FIFO で購読先が SQS 標準キューだと順序も一意性も崩れ、DLQ がないと届かなかったメッセージは捨てられる ([AWS: SNS FIFO ordering](https://docs.aws.amazon.com/sns/latest/dg/fifo-topic-message-ordering.html))。ファンアウトするなら、購読先も FIFO にして DLQ を必ず付けること。

エンベロープは CloudEvents 1.0（最新リリースは v1.0.2）の JSON 形式にする。必須属性は `id`・`source`・`specversion`・`type` で、`source` + `id` の一意性はプロデューサの責任になる ([CloudEvents spec](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md))。13 ある公式拡張にテナントはない ([extensions README](https://github.com/cloudevents/spec/blob/main/cloudevents/extensions/README.md))。そこで独自拡張 `tenantid` を定義する（小文字英数字で 20 文字以内という命名規則に合う）。その値は、アウトボックスに INSERT するときに、検証済みのセッションのテナントから書き込む。順序キーは Partitioning 拡張の `partitionkey` に aggregate ID を入れ、トレースは Distributed Tracing 拡張の `traceparent` で運ぶ。CloudEvents には Kafka・NATS・AMQP・MQTT・HTTP のバインディングはあるが、**SQS のバインディングはない** ([cloudevents/spec](https://github.com/cloudevents/spec))。Kafka では binary mode（属性は `ce_` ヘッダ）を使う ([Kafka binding](https://github.com/cloudevents/spec/blob/main/cloudevents/bindings/kafka-protocol-binding.md))。SQS / SNS では、structured JSON を本文に入れる。SQS のメッセージ属性は 10 個までなので、フィルタに使う `type` と `tenantid` だけを属性に複製すればよい ([AWS: SQS quotas](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html))。SQS FIFO の重複排除 ID には、content-based を使わずイベント ID を明示する。content-based は本文だけをハッシュするので、本文がたまたま同じ別のイベントを誤って捨てうる。スキーマの記述には AsyncAPI 3.0（operation が `send` / `receive` でチャネルを指す）を生成物に足すのが安上がりだ ([AsyncAPI 3.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0))。Confluent Schema Registry（既定の互換モードは BACKWARD）は Avro や Protobuf を使うときのアダプタ側のオプションに回す ([Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html))。

Port は、トランスポートに依存しないものを三つにとどめる。一つ目は Use case が使う既存の `EventPublisher` で、本番の実装は同じトランザクションでアウトボックスに書く。二つ目は中継が使う `MessageTransport.send(envelopes)` で、これがブローカーに依存する唯一の Port になる。三つ目は受信ハンドラで、テナントのコンテキストを作り、`parse_event` で型付きのイベントに戻し、policy を選び、`(policy 名, event id)` を冪等キーにして Use case を呼ぶ。ここで生成器の変更が一つ要る。今の `idempotency_key` は「コマンドの必須入力フィールド」に限られるので、policy から呼ばれる Use case はそのままでは `IdempotencyStore` を受け取れない。コマンドにイベント ID のフィールドを持たせるか、ハンドラ側に dedup を差し込む生成を足して、初めて既存の仕組みが inbox になる。再試行と DLQ は、SQS の redrive、Kafka の DLT、NATS の MaxDeliver といったインフラ側に置き、生成コードはループを持たない。クライアントは、TS + Kafka なら **kafkajs ではなく `@confluentinc/kafka-javascript`** を使う。kafkajs は npm の最新が 2023-02 の 2.2.4 のままで ([npm kafkajs](https://www.npmjs.com/package/kafkajs))、Confluent 版は librdkafka ベースで KafkaJS 風の API を持ち、2026-10 に 1.11.0 が出ている ([Confluent blog](https://www.confluent.io/blog/introducing-confluent-kafka-javascript/), [npm](https://www.npmjs.com/package/@confluentinc/kafka-javascript))。ただしネイティブアドオンなので、Bun で動くかは確かめていない。Python は `confluent-kafka` 2.16.0（asyncio 用の `AIOProducer` / `AIOConsumer` あり）を使う ([PyPI](https://pypi.org/project/confluent-kafka/), [Confluent blog](https://www.confluent.io/blog/kafka-client-updates-kip-848-oauth/))。SQS は `@aws-sdk/client-sqs` と boto3 を使う。

基盤の位置づけをまとめておく。AWS が前提なら SQS（+ SNS FIFO）が既定になる。運用するものがほぼなく、AWS 自身も、厳密な順序が要らないなら標準キューのほうが安く管理しやすいと書いている ([AWS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/high-throughput-fifo.html))。弱みは、リプレイがなく保持が最大 14 日なことだ。リプレイは SNS FIFO のアーカイブにしかない ([SNS quotas](https://docs.aws.amazon.com/general/latest/gr/sns.html))。Kafka は、ログとしての再生、後から足すコンシューマ、Debezium の素直な利用が要るときに選ぶ。Kafka 4.2 では share groups（KIP-932）がキュー的な使い方を本番に持ち込んだ ([Apache Kafka 4.2.0](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/))。ただし 4.2 のリリース日はソースによって食い違う。Redpanda は Kafka API 互換でトランザクションも持つ ([Redpanda docs](https://docs.redpanda.com/25.3/develop/transactions))。単一バイナリなので、CI で Kafka の代わりに使うのに向く。2026 年のライセンスは確認できていない。NATS JetStream は軽量で CloudEvents のバインディングもあり、セルフホストや非 AWS 環境での候補になる。Pub/Sub は GCP での SQS 相当だが、ordering key ごとの publish が 1 MBps に限られ ([Google Cloud: ordering](https://docs.cloud.google.com/pubsub/docs/ordering))、ordering と exactly-once を組み合わせるとスループットは毎秒数千程度まで下がる。料金の一次資料は集めておらず、この比較は定性的なものにとどまる。

## OpenAPI 3.1 を Zod から派生させ、gRPC は主契約にしない

ブラウザ対応が必須である以上、素の gRPC を主契約にする理由はない。gRPC-Web にはサーバー側の対応か Envoy などのプロキシが要り、ブラウザからは **client streaming と双方向ストリーミングが使えない** ([Microsoft Learn](https://learn.microsoft.com/en-us/aspnet/core/grpc/grpcweb))。もっと根本的な問題もある。.proto を契約にすると、Zod / Pydantic と並ぶ第二のスキーマ源が生まれる。そして ProtoJSON の規則は今の Zod JSON 契約とワイヤー互換ではない。int64 は文字列になり、既定値は省略され、名前は lowerCamelCase になり、未知のフィールドは既定で拒否される ([protobuf.dev JSON](https://protobuf.dev/programming-guides/json/))。protobuf には標準の decimal 型もない（`google.type.Decimal` は文字列 1 つ）([Google common protos](https://docs.cloud.google.com/java/docs/reference/proto-google-common-protos/latest/com.google.type.Decimal))。判別共用体のイベントは、`oneof` だと JSON 上の形がタグフィールドからキー名に変わる。どれも、DDD の値型をワイヤーに載せるときに摩擦を生む。

OpenAPI 3.1 なら、既存の契約から機械的に導ける。Zod 4（現行 4.6.6）の `z.toJSONSchema()` は既定で JSON Schema Draft 2020-12 を出し、レジストリのメタデータを付けた ID 付きスキーマを `$ref` で相互参照させられる ([zod.dev/json-schema](https://zod.dev/json-schema))。ただし `date`・`bigint`・`transform` は既定で例外になる。なので、Instant は RFC 3339 の `format: date-time` の文字列、Decimal は pattern 付きの文字列として、ワイヤー上の型を明示する必要がある。paths の組み立てまで含めるなら、zod-openapi 6.x（OpenAPI 3.1.0 / 3.1.1 対応、`.meta()` ベース）が軽い ([zod-openapi](https://github.com/samchungy/zod-openapi))。生成器はパスもメソッドもスキーマもすべて知っているので、Hono の `@hono/zod-openapi` のようなフレームワーク依存は要らない。Python 側は FastAPI が PR #9770 から OpenAPI 3.1.0 を出している ([FastAPI release notes](https://github.com/fastapi/fastapi/blob/master/docs/en/docs/release-notes.md))。ただし入力と出力でスキーマを分けたときの命名は、zod-openapi が `outputIdSuffix`、FastAPI が `-Input` / `-Output` と異なる ([FastAPI](https://fastapi.tiangolo.com/how-to/separate-openapi-schemas/))。TS と Python の二つの仕様を突き合わせるなら、生成器の側で命名規則を揃えておく必要がある。互換性は **oasdiff**（Apache-2.0、`breaking` サブコマンドと GitHub Action あり、v1.33.0）で、main の仕様との差分として検査する ([oasdiff](https://github.com/oasdiff/oasdiff))。終了コードを制御するフラグの細部は確認していない。エラーは RFC 9457 の `application/problem+json` で返し、ドメインのエラーコードを拡張メンバーに入れる ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html))。

TanStack Query との統合については、第三者の生成器に乗り換えない。@hey-api/openapi-ts は queryOptions / infiniteQueryOptions / mutationOptions を生成できるが、まだ 0.99.0 で 1.0 に届いておらず、キーは `_id` や `baseUrl` を含む独自の形だ ([heyapi.dev](https://heyapi.dev/openapi-ts/plugins/tanstack-query))。orval のキーは path 文字列の配列 ([orval.dev](https://orval.dev/docs/guides/react-query))、openapi-react-query は 0.5.4 で infinite のヘルパーがまだ要望段階にある ([issue #2462](https://github.com/openapi-ts/openapi-typescript/issues/2462))。どれも既存の TkDodo 流のオブジェクトキーとは互換がない。社内のフロントは自前のファクトリを使い続け、OpenAPI は外部利用者・他言語 SDK・テストのための派生物と位置づけるのが整合的だ。TypeSpec は typespec-stable 1.17.0 まで来ているが、Rest や Streams は preview のままだ ([TypeSpec releases](https://github.com/microsoft/typespec/releases), [typespec.io](https://typespec.io/docs/emitters/openapi3/reference/emitter/))。それ以上に、DSL がすでに唯一の正なので、TypeSpec を源にするとスキーマ源が三つ目になる。採る意味があるとすれば、生成器が TypeSpec を出力する場合に限られる。

ConnectRPC は、gRPC 系を使いたくなったときの答えになる。unary は HTTP/1.1 上の素の POST（JSON か protobuf）なので、プロキシなしでブラウザから呼べる。`NO_SIDE_EFFECTS` の RPC は GET でキャッシュでき、同じサーバーで gRPC と gRPC-Web も話せる ([Connect protocol](https://connectrpc.com/docs/protocol/))。connect-es は v2.2.0 で安定しており ([release](https://github.com/connectrpc/connect-es/releases/tag/v2.2.0))、connect-query v2.3.1 が TanStack Query と統合する。ただし connect-query は**unary だけの対応**で、キーは `"connect-query"` で始まる独自の形だ ([connect-query-es](https://github.com/connectrpc/connect-query-es))。Python 側の `connectrpc` は conformance に合格しているが、**0.12.1 で 1.0 前**だ。0.12.0 では受信上限の既定が無制限から 4MB に変わるなど、既定の挙動が変わっている ([connect-py releases](https://github.com/connectrpc/connect-py/releases), [v0.12.0](https://github.com/connectrpc/connect-py/releases/tag/v0.12.0))。Web 標準の Request→Response で動かす公開アダプタもなく、`createConnectRouter` と `universalServerRequestFromFetch` から自分で組むことになる ([universal-fetch.ts](https://github.com/connectrpc/connect-es/blob/main/packages/connect/src/protocol/universal-fetch.ts))。したがって Connect は、二つの条件がそろったときだけのオプションにする。社内のサービス間通信やストリーミングが要ること、そして生成器が DSL から .proto も出すこと（第二のスキーマ源を作らないため）だ。その場合は CI で `buf breaking --against '.git#branch=main'` を回し、カテゴリは JSON を壊すリネームも捕まえる **WIRE_JSON 以上**にする ([buf rules](https://buf.build/docs/breaking/rules/))。

## OTel API を生成コードが直接呼ぶことが、正しい抽象化になる

「OpenTelemetry は必ず入れたいが、トレースは抽象化したい」という要望には、自前の Tracer / Telemetry ポートを作らない、と答える。OTel の仕様は、計装する側が **API だけ**に依存し、SDK はアプリが選ぶ設計になっている。SDK がなければ、API の呼び出しは最小限のオーバーヘッドの no-op になる ([OTel Client Design Principles](https://opentelemetry.io/docs/specs/otel/library-guidelines/))。つまりベンダー中立性も「入れても使わなければ無害」という性質も、OTel API がすでに提供している。2026 年の OTel 公式ブログ「Don't Wrap OpenTelemetry」は、独自ラッパーが四つの害をもたらすと挙げる。計測のたびのヒープ確保、名前による計測器の検索、開発者が OTel ではなくラッパーを学ぶこと、API の上にもう一つ API を保守することだ。そのうえで、承認された属性や命名を強制したい場合には「**独自スキーマから型安全なコードを生成し、生成コードが OTel を直接呼ぶ**」形を正当な例外として勧めている ([OTel Blog](https://opentelemetry.io/blog/2026/dont-wrap-opentelemetry/))。これはコード生成器のやり方そのものだ。テストのためのラッパーも要らない、と同じ記事は書いている。各 SDK に InMemory エクスポータがあるからだ。

ポート案を擁護するなら、最も強い論点は「ドメインに OTel の型を漏らさない」ことと「テストで偽物に差し替えられる」ことだろう。前者は層の分け方で満たせる。エンティティ・値オブジェクト・ドメインサービスは OTel を一切 import しない。生成したユースケース・クエリ・ポリシーハンドラ・HTTP ハンドラ（アプリケーション層とインフラ層）は `opentelemetry-api` / `@opentelemetry/api` を直接呼ぶ。SDK とエクスポータの組み立ては、コンポジションルートの雛形か利用者の設定に置く。後者は InMemory エクスポータで満たせる。逆にポートを作ると、コンテキスト伝播、Span link、自動計装スパンとの親子関係のどれかを再実装するか取りこぼすことになる（この点は記事が直接は述べておらず、推論だ）。生成するユースケース本体を読みやすく保ちたいなら、スパンの開始と終了をデコレータ（Python）や高階関数（TS）として生成すればよい。本体は、必要なときだけ現在のスパンに属性を足す。これはランタイムのラッパーではなく、生成時に織り込む形なので、記事の例外の範囲に収まる。OTel の安定度は、Python・JS とも Traces と Metrics が Stable、Logs は Development だ ([OTel Status](https://opentelemetry.io/status/))。Span Events API（`AddEvent` / `RecordException`）は非推奨化が進んでおり、「events are logs with names」としてスパンに相関づけたログに一本化される ([OTel Blog: Deprecating Span Events](https://opentelemetry.io/blog/2026/deprecating-span-events/))。生成コードでは、例外はスパンの status と `error.type` で表し、ドメインエラーの詳細は相関づけたログで出す。ログは言語標準のロガー（Python `logging`、Node は pino）に書き、OTel へはブリッジで送る ([OTel Python logs example](https://opentelemetry.io/docs/zero-code/python/logs-example/))。

セマンティック規約では、HTTP のスパンとメトリクスは Stable だ。`http.server.request.duration` は秒単位のヒストグラムで、`http.route` には生のパスではなく低カーディナリティのテンプレートを入れなければならない ([semconv HTTP metrics](https://opentelemetry.io/docs/specs/semconv/http/http-metrics/))。生成器はルートテンプレートを確実に知っているので、アクティブなスパンに `http.route` を足すコードを出せば、フレームワーク計装が取りこぼす場面を補える。DB スパンの規約のページは Stable と書いているが、移行ガイドの記述とは食い違っている。規約では、スパン名は `{db.query.summary}`、なければ `{db.operation.name} {target}` とする。パラメータ化されたクエリの本文は既定で収集してよく、**パラメータの値は PII を含みうるので opt-in** だ ([semconv DB spans](https://opentelemetry.io/docs/specs/semconv/database/database-spans/))。pg_trgm の検索語は個人情報になりやすいので、値は記録しない。Messaging の規約はまだ Development なので ([semconv messaging](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/))、`messaging.*` は最小限にする。独自属性は既存の名前空間を接頭辞にしてはいけない ([semconv naming](https://opentelemetry.io/docs/specs/semconv/general/naming/))。`app.*` はすでに semconv の名前空間で、テナントに当たる標準属性もない ([registry: app](https://opentelemetry.io/docs/specs/semconv/registry/attributes/app/))。そこで `ddd_presenter.use_case.name`・`ddd_presenter.tenant.id`・`ddd_presenter.outcome` のような生成器固有の接頭辞を使う。接頭辞は利用者が変えられるようにしておく。メトリクスには**テナントを既定で付けない**。SDK の既定のカーディナリティ上限は 2000 で、超えた分は `otel.metric.overflow=true` という一つの系列に潰れる ([Metrics SDK spec](https://opentelemetry.io/docs/specs/otel/metrics/sdk/))。そうなると全テナントの数値が壊れる。テナント別の内訳はスパンとログから取る。生成器が足すメトリクスは、ユースケース・クエリ・ポリシーの所要時間のヒストグラム、ドメインルール違反のカウンタ、レート制限による拒否のカウンタに絞る。HTTP と DB の RED は自動計装に任せる。

最大の危険は Baggage だ。W3C Baggage はまだ Candidate Recommendation で、値は第三者のシステムにも伝わりうる。仕様自身が「Systems MUST assess the risk of header abuse」と書き、受け手に悪意ある入力への防御を求めている ([W3C Baggage](https://www.w3.org/TR/baggage/))。**テナント ID を Baggage で運び、受信側でそれを信じて認可や RLS に使えば、ヘッダを書き換えるだけでテナントを越えられる穴になる。** 自動計装された fetch や undici が外部 API にそのヘッダを漏らす危険もある。テナントは、HTTP では毎リクエスト検証済みの JWT から取り出す。非同期では、アウトボックスに永続化したエンベロープの `tenantid` から取る。スパン属性はそのうえで付ける。メッセージ経由の伝播は、作成時のコンテキストを `traceparent` としてエンベロープに注入する。処理側のスパンは周囲のスパンの子にし、作成時のコンテキストへ link を張る。これが semconv の推奨だ ([semconv messaging](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/))。CloudEvents の Distributed Tracing 拡張は、伝送の起点のトレースだけを運び、ホップごとの情報は載せないと定めている ([CloudEvents distributed tracing](https://github.com/cloudevents/spec/blob/main/cloudevents/extensions/distributed-tracing.md))。自動計装との関係では、生成コードは独自の TracerProvider を作らず `trace.get_tracer(...)` を使うだけでよい。そうすれば、自動計装の HTTP サーバースパン → 生成したユースケースのスパン → psycopg / pg の DB スパン、と自然に入れ子になる。二重スパンを避けるため、生成するリポジトリでは既定で DB スパンを手動で作らない。ただし Bun では、Node の preload 方式がそのままでは使えない。プログラムから初期化する手順を案内しているのも Datadog の文書だけで、しかもこれは検索要約で確認しただけの弱い情報だ ([Datadog](https://docs.datadoghq.com/opentelemetry/guide/instrument_unsupported_runtimes/))。自動計装が効く保証はないので、`db_spans: auto | manual | off` のような生成オプションを用意し、効かない環境だけ手動にする。生成するテストは、InMemorySpanExporter でスパン名・属性・親子関係・status を検証するものと、SDK を入れない no-op の経路でも動くことを確かめるものを組にする。

## DSL の制約から strategy を生成することが、最大の差別化になる

プロパティベーステストは、生成器が既存のどの道具よりもうまくやれる領域だ。スキーマから自動で生成器を導く道は、2026 年時点でどちらの言語でも閉じている。Pydantic v2 は Hypothesis プラグインの同梱をやめ、書き直しの issue は open のままで、メンテナーは「nothing planned for the moment」と書いている ([pydantic#4682](https://github.com/pydantic/pydantic/issues/4682))。代わりに挙がる hypothesis-jsonschema も 2024-02 からリリースがない ([PyPI](https://pypi.org/project/hypothesis-jsonschema/))。TS 側の zod-fast-check は **Zod 3 / fast-check 3 止まり**で、最新は 2023-09 ([npm zod-fast-check](https://registry.npmjs.org/zod-fast-check))。公式の `@fast-check/zod` は存在しない。ローカルで試したところ（URL なし、hypothesis 6.141.1。最新版では未確認）、`st.from_type` は数値と長さの制約は守るが、Decimal の桁指定を無視して落ち、`model_validator` の複合条件も破る入力を作った。Aggregate の不変条件を満たす値は、型からの推論では作れないということだ。一方、DSL はすでに制約と不変条件を持っている。だから生成器は、**strategy / arbitrary をコードとして直接出す**べきだ。Decimal には範囲と桁を明示した `st.decimals`、フィールドをまたぐ不変条件は filter ではなく構成的な生成で作る。Hypothesis 6.169.0 と fast-check 4.10.2 はどちらも活発で ([PyPI hypothesis](https://pypi.org/project/hypothesis/), [npm fast-check](https://registry.npmjs.org/fast-check))、vitest には公式の `@fast-check/vitest` 0.5.0（vitest 4 / 5 対応）がある ([npm](https://registry.npmjs.org/@fast-check/vitest))。bun test には公式コネクタがないので、その場合は素の `fc.assert` を出す。

状態機械テストは、DSL とほぼ一対一に対応する。Hypothesis の `RuleBasedStateMachine` では、`@rule` が operation、`@precondition` が状態ガード（`assume` より推奨されている）、`@invariant` が毎ステップ後の不変条件、`Bundle` が作成した Aggregate の ID の置き場になる ([Hypothesis stateful](https://hypothesis.readthedocs.io/en/latest/stateful.html))。fast-check の `fc.commands` では、`check(model)` がガード、`run(model, real)` が実行とアサートに当たる。非同期用の `asyncModelRun` があり、失敗したシナリオは効率よく縮小される ([fast-check model-based](https://fast-check.dev/docs/advanced/model-based-testing/))。モデル（オラクル）は DSL の `changes` から生成できる。ただし注意が要る。実装とオラクルを同じ DSL から生成すると、両方に同じ誤りが入りうる。このテストが保証するのは「到達しうるすべての状態で不変条件が保たれる」「ガード違反は必ず宣言済みのエラーになる」「JSON の往復」までで、`changes` の意味の正しさは保証しない。その点はドキュメントに明記すべきだ。最も低リスクな入り口は、既存の JSON 往復テスト、違反値テスト、冪等性テストをプロパティに一般化することだ。Scott Wlaschin の分類でいえば、それぞれ "there and back again"、不変量、冪等に当たる ([F# for Fun and Profit](https://fsharpforfunandprofit.com/posts/property-based-testing-2/))。CI では、Hypothesis が環境変数 `CI` を見て自動で derandomize し、例の保存も無効にする ([Hypothesis API](https://hypothesis.readthedocs.io/en/latest/reference/api.html))。PR では控えめな例数で回し、nightly で多く回す二段構えにする。

契約テストでは、クライアントとサーバーを同じモデルから生成する以上、消費者駆動の Pact が足す検出力は小さい。Pact の公式 FAQ も「消費者が誰か分からないなら Pact は向かない」とし、公開 API には OpenAPI を挙げている ([Pact docs](https://docs.pact.io/faq/convinceme))。pact-python 3.x は Rust FFI に移って健在だ ([MIGRATION.md](https://github.com/pact-foundation/pact-python/blob/main/MIGRATION.md)) が、生成はしない。利用者が第三者の消費者を持つ場合のガイドにとどめる。価値があるのは三つの場面で、生成後に利用者がハンドラに手を入れた場合、デプロイの版ずれ、第三者の消費者だ。これらを捕まえるのが **Schemathesis**（4.30.1）になる。OpenAPI 3.0〜3.2 から property-based なテストを自動生成し、失敗ごとに最小の curl 再現コマンドを出す。OpenAPI links に沿った状態遷移テストもできる ([Schemathesis docs](https://schemathesis.readthedocs.io/en/stable/), [stateful guide](https://schemathesis.readthedocs.io/en/stable/guides/stateful-testing/))。言語に依存しない CLI なので、TS のサーバーにも使える。Specmatic（MIT）は OpenAPI と AsyncAPI の両方を実行可能な契約として扱い、仕様の二つの版を比べる contract-vs-contract も持つ ([specmatic](https://github.com/specmatic/specmatic))。ただし OSS 版と有償版の境界が明示されていない。版の間の破壊的変更は oasdiff で足りるので、Specmatic は AsyncAPI の非同期契約が要るときの候補にとどめる。

BDD では、`bddgen` は playwright-bdd（v9.2.1）の CLI で、`.feature` から Playwright のテストファイルを生成してから実行する ([playwright-bdd docs](https://github.com/vitalets/playwright-bdd/blob/main/docs/index.md), [FAQ](https://github.com/vitalets/playwright-bdd/blob/main/docs/faq.md))。UI レベルの受け入れテストのための道具で、Playwright の runner が前提になる。生成器が UI を持たない以上、主役にはならない。pytest-bdd 9.0.0（公式 Gherkin パーサーに移行済み）と Cucumber.js 13.3.0 はどちらも活発だ ([pytest-bdd](https://pypi.org/project/pytest-bdd/), [npm @cucumber/cucumber](https://registry.npmjs.org/@cucumber/cucumber))。しかし DSL のシナリオはすでに例示テストとして生成されている。`.feature` とステップ定義まで生成すると同じ検証が二系統になり、人が直した Gherkin も再生成で上書きされる。Cucumber の作者 Aslak Hellesøy は Cucumber を協働の道具とし、「regression tests are a by-product」と述べている ([InfoQ](https://www.infoq.com/news/2015/03/bdd-cucumber-testing/))。機械生成の Gherkin は、その本来の役割を果たせない。現実的なのは、DSL のシナリオを宣言的な `.feature` に変換して、**実行しない生きたドキュメント**として出すことだ。DSL のシナリオはもともとドメインの言葉で書かれているので、Cucumber が勧める宣言的な書き方にも合う ([Cucumber: better Gherkin](https://cucumber.io/docs/bdd/better-gherkin/))。UI 受け入れテストを利用者が書くなら、生成器はステップの文言と、HTTP API を叩く API レベルのステップ定義までを出す。それを利用者が playwright-bdd に載せる、という分担なら成り立つ。

## 依存の順に六段で入れる

順番は費用ではなく依存関係から決まる。第一段は二つを並行して進める。一つは DB の差分の流れで、純粋な状態の DDL モードを足し、psqldef で往復を確かめ、`--check` を CI に入れ、マイグレーション用ロールを設計し、docs/05 の migra の記述を差し替える。もう一つはプロパティベーステストで、strategy の生成と既存テストの一般化から始める。PBT は前提を何も持たないので、待つ理由がない。アウトボックスのテーブルは差分の流れに乗せて配る必要があるので、DB が先に来る。第二段は OTel API の埋め込みだ。エンベロープの `traceparent` と、ポリシー処理のスパンの link はこれが前提になる。第三段は OpenAPI 3.1 の出力で、oasdiff と Schemathesis はこれがないと動かない。第四段で、アウトボックス、ポーリング中継、CloudEvents のエンベロープ、受信ハンドラ、AsyncAPI を入れる。その前に、policy から呼ばれる Use case に冪等キーを渡す生成器の変更を済ませておく。第五段は Aggregate ごとの状態機械テストの生成で、第一段の strategy の上に乗る。最後の第六段は、実行しない `.feature` ドキュメントと、条件がそろった場合の Connect / .proto 出力だ。

| テーマ | 採用する | 採用しない（またはオプション） | 理由 |
|---|---|---|---|
| DB アクセス | 生成器の型付きコード（`$n::type` を常に付ける）、`sqlc vet` + `db-prepare` を検証用に | sqlc の Python / TS プラグイン、Drizzle、Kysely、SQLAlchemy | プラグインの停滞と SQLAlchemy への依存、型の一次情報が二重になる ([issue #94](https://github.com/sqlc-dev/sqlc-gen-python/issues/94)) |
| マイグレーション | psqldef v3.11.19 以上（`--check`、`manage.extension` で pg_trgm に絞る）、次点は pgschema | Atlas（予算があれば Pro）、Alembic、drizzle-kit、migra、Liquibase | RLS・拡張・opclass を無償で扱える。Atlas は RLS が Pro、migra は deprecated ([Atlas features](https://atlasgo.io/features)) |
| ゼロダウンタイム | 必要時のみ pgroll（PG 15 以上） | reshape | RLS の尊重は security_invoker が前提、reshape は継続性が不明 |
| メッセージング | アウトボックス + ポーリング中継、inbox、CloudEvents 1.0 + `tenantid` / `partitionkey`、SQS（標準 + fair / FIFO）と SNS FIFO | 既定の CDC（Debezium）、Kafka EOS、テナントを順序キーにすること、kafkajs | SQS の sink がない、PGlite に WAL がない、EOS は DB を守らない ([Debezium Server](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)) |
| 他のブローカー | Kafka / Redpanda（再生と長期保持）、NATS（セルフホスト）、Pub/Sub（GCP）をアダプタとして | ― | Port の下で差し替えるオプション |
| API | OpenAPI 3.1（Zod から派生、FastAPI）、oasdiff、RFC 9457、自前の TanStack Query ファクトリ | 素の gRPC / gRPC-Web、TypeSpec を源にすること、hey-api / orval への置き換え | ブラウザの制約、スキーマ源の増加、キー形式の非互換 |
| 内部 RPC | 条件付きで ConnectRPC + `buf breaking`（WIRE_JSON） | ― | connect-python が 0.x、DSL から .proto を出す場合に限る |
| 可観測性 | OTel API を直接呼ぶ生成コード、`ddd_presenter.*` 属性、InMemory エクスポータのテスト、ログはブリッジ経由 | 自前の Tracer ポート、Baggage でのテナント伝播、メトリクスへのテナント属性、Span Events | 公式の「Don't Wrap」、ヘッダ偽装の危険、カーディナリティ上限 2000 |
| テスト | 生成する strategy / arbitrary、RuleBasedStateMachine / `fc.commands`、Schemathesis | zod-fast-check、Pydantic の自動推論、Pact の生成、実行する BDD | Zod 4 / Pydantic v2 に未対応、両側を生成するので Pact の効果が薄い |
| BDD | 読み取り専用の `.feature` ドキュメント、API レベルのステップ定義 | bddgen による UI テストの生成、pytest-bdd / Cucumber.js による二重実行 | 例示テストとの重複、機械生成の Gherkin は協働の役に立たない |

## 結論

調べた結果、問いの前提がいくつか入れ替わった。「生成器が SQL を出し、型付きアクセスは sqlc に渡す」という想定は、2026 年の sqlc プラグインの状態を見ると逆向きで、型付きアクセスこそ生成器が手放してはいけない部分だった。同じく「トレースを自前の層で抽象化する」という想定も、OTel 自身がすでにその抽象化の層であり、コード生成は公式が認める唯一のきれいな包み方だと分かった。どちらも、道具の成熟度が足りないから生成器が頑張る、という話ではない。DSL が型・制約・不変条件・テナントの文脈という一次情報を持っているので、それを外の道具に推論し直させるたびに、ずれと保守の負担が生まれる、という構造の話だ。

この構造から、もう一つ実務的な含意が出てくる。生成器の価値は、出力の量よりも「どの検証を CI に機械的に差し込めるか」で決まるようになる。psqldef の `--check`、oasdiff の `breaking`、Schemathesis、状態機械テスト、InMemory エクスポータでのスパン検証は、いずれも生成器が DSL を知っているからこそ偽陽性の少ない門になる。逆に、まだ確かめていない点はすべて「実際に通してみる」作業で決着する。冪等な bootstrap DDL を psqldef が受け付けるか、Bun で自動計装とネイティブの Kafka クライアントが動くか、`xid8` を使う中継が長いトランザクションの下でどれだけ遅れるかの三つだ。最初の一歩は、cleaning-platform の例を使ったこの三つの検証にするべきだ。
