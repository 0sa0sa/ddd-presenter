# 03. Functional Requirements

## 1. 優先度

- **P0:** MVPで必須。ないと顧客の実リポジトリで価値を検証できない。
- **P1:** 初期有料版までに必要。
- **P2:** 顧客検証後に判断。

各IDは課題、設計、実装、受け入れテストで共通利用する。

## 2. ワークスペースとプロジェクト

### FR-001 — プロジェクトを作成する（P0）

利用者はプロジェクト名、説明、既定言語を指定してプロジェクトを作成できる。

**受け入れ条件:**

- プロジェクトには一意な識別子とモデル形式のバージョンがある。
- 空のプロジェクトには開始用サンプルモデルとチュートリアルを表示する。
- プロジェクトのエクスポート・削除ができる。

### FR-002 — bounded contextを管理する（P0）

利用者はbounded contextを追加し、責務、用語、含まれるモデル要素を管理できる。

**受け入れ条件:**

- 要素は必ず一つのContextに所属する。
- Contextを越える参照には明示的な境界型またはイベント契約を使う。
- Contextを削除する際、配下要素と参照への影響を事前に表示する。

## 3. モデル編集

### FR-010 — Entityを定義する（P0）

利用者はEntityの名前、識別子、属性、生成方法、状態変更操作を定義できる。

**受け入れ条件:**

- 識別子の型と同一性比較の意味が明示される。
- Entityの状態を外部から無条件に書き換える生成コードを作らない。
- 属性の型、必須性、コレクション種別、制約を検証する。
- 同一Context内の重複名、予約語、不正な型参照を報告する。

### FR-011 — Value Objectを定義する（P0）

利用者はValue Objectとその属性・制約・正規化規則を定義できる。

**受け入れ条件:**

- 既定では値ベースの等価性と不変性を持つ。
- 文字列長、範囲、パターン、精度、列挙値などの制約を定義できる。
- Value Objectを別Aggregateで再利用する場合、依存方向を検証する。
- 任意のPythonコードを条件欄に直接埋め込まない。

### FR-012 — Aggregateを定義する（P0）

利用者はAggregate Root、内部Entity、Value Object、境界、操作を構成する。

**受け入れ条件:**

- 各AggregateにRootが一つだけある。
- Rootを通さず内部Entityを永続化・変更する操作を警告する。
- Aggregate境界を越える更新には参照IDまたはDomain Eventを使う。
- 大きすぎるAggregate候補を診断するが、ツールが自動分割を確定しない。

### FR-013 — Invariantを定義する（P0）

利用者は常に守る条件を、名前、型付き条件式、違反時エラー、評価タイミングと共に定義する。

**受け入れ条件:**

- Invariantはコンストラクタと指定された状態遷移後に自動評価される。
- 条件式はDSLの型付き構文木として解析し、Python `eval`を使わない。
- エラー名、メッセージ、必要なら識別子などの情報を定義できる。
- どの生成操作がどのInvariantを評価するか追跡できる。
- 外部副作用、現在時刻、ネットワーク、DBアクセスをInvariant式から実行できない。

### FR-014 — StateGuardを定義する（P0）

利用者は特定の操作時に確認する条件をStateGuardとして定義する。

**受け入れ条件:**

- StateGuardは自動Invariant一覧の対象にならない。
- 生成APIは`checks() -> bool`と、ドメイン例外を送出する`assert_holds()`の両方を提供する。Pythonの`assert`は予約語のためメソッド名に使わない。
- 引数を含む場合、必須引数と評価時刻の供給元を明示する。
- 条件が成立しない場合に該当操作を呼べないよう、生成された操作の前提条件として関連付けられる。

### FR-015 — 状態遷移とDomain Eventを定義する（P0）

利用者は操作の入力、前提ガード、状態変更、返却値、発生イベントを定義する。

**受け入れ条件:**

- 状態変更は定義済みフィールドへの型整合する代入に限る。
- 複数フィールドの変更を一つの遷移として検証し、不正な中間状態を外部へ露出しない。
- イベントは発生条件・型付きpayload・発生元の操作を持つ。
- 更新後にInvariantを検証する。
- 同じ遷移で同じイベントが重複定義された場合に診断する。

### FR-016 — Domain Errorを定義する（P0）

利用者は業務上の失敗を名前付きエラーとして定義し、GuardやUse Caseから参照できる。

**受け入れ条件:**

- 例外名と機械可読コードが一意。
- 表示メッセージと内部診断情報を分離する。
- HTTP statusや特定Web frameworkにドメインエラーを直接依存させない。

## 4. ユースケースと振る舞い

### FR-020 — Use Caseを定義する（P0）

利用者はUse Case名、Actor、Command入力、結果、業務手順を定義できる。

**受け入れ条件:**

- 入力は型付きフィールドと制約を持つ。
- 手順は名前付きステップで表し、Domain操作の呼び出し順を可視化する。
- Repository読み込み、Domain操作、保存、イベント通知等はPort経由で表す。
- 条件分岐は名前付きStateGuardまたはPolicyを参照する。
- トランザクション開始・確定・失敗時の扱いをモデル上で区別できる。
- 外部I/Oの具体的な実装をドメイン層へ生成しない。

### FR-021 — シナリオと受け入れ条件を定義する（P0）

利用者はGiven-When-Then形式で正常系、境界値、業務例外を定義する。

**受け入れ条件:**

- シナリオはUse Case、Rule、結果、発生イベントと参照リンクを持つ。
- P0のシナリオからpytestテストを生成する。
- モデル変更でシナリオが無効になった場合、生成前にエラーとして示す。
- 期待結果が曖昧なシナリオを成功扱いしない。

### FR-022 — モデルをシミュレーションする（P1）

利用者は宣言済みの手順と条件を使い、指定シナリオの分岐・イベント・状態差分を確認できる。

**受け入れ条件:**

- 実装されていない手書き拡張は「未評価」と表示する。
- シミュレーション結果に使ったモデル版と前提データを表示する。
- 実行可能コードをWebサーバー上で無制限に実行しない。

## 5. 検証・生成・連携

### FR-030 — モデルを検証する（P0）

**受け入れ条件:**

- 構文、参照、型、名前重複、Aggregate境界、循環依存、Rule評価可能性を診断する。
- 診断には重大度、位置、原因、修正案を含める。
- 同じモデルはWebとCLIで同じ意味検証結果を返す。
- 生成を止めるエラーと警告を区別する。

### FR-031 — Pythonコードを生成する（P0）

**受け入れ条件:**

- Entity / Value Object / Aggregate / Command / Event / Error / Port / Use Caseの型と構造を生成する。
- 定義された条件式を読みやすいPythonとして出力する。
- Invariant / StateGuardの評価箇所がDSL定義と一致する。
- 指定シナリオのpytestテストを生成する。
- コードは一般的なPythonツールで実行・型検査できる。
- 同じ入力モデル・ジェネレータ版・設定から同じ出力を得る。

### FR-032 — 生成前の差分を確認する（P0）

**受け入れ条件:**

- 追加、変更、削除、手書きファイルとの衝突を分類する。
- 手書き領域を上書きする操作は既定で禁止する。
- 生成マニフェストにモデル版、ジェネレータ版、生成対象ファイルを記録する。
- 破壊的変更を含む場合に理由と影響範囲を表示する。

### FR-033 — モデルをインポート・エクスポートする（P0）

**受け入れ条件:**

- Web UIとCLIの両方でバージョン付きYAMLを読み書きできる。
- モデル形式の旧版を新しい版へ移行するツールを提供する。
- 顧客のモデルをサービスから一括エクスポートできる。
- エクスポートファイルをサービス利用終了後もCLIで利用できる。

### FR-034 — CLIとCIで使う（P0）

CLIは少なくとも`validate`、`generate`、`diff`、`version`を提供する。

**受け入れ条件:**

- CIで非対話実行でき、エラー時に非ゼロ終了コードを返す。
- 同じ入力でWebとCLIの意味検証・生成結果が一致する。
- CLIはソースコードをサービスへアップロードせずに実行できる。
- ロックファイル等でジェネレータ版を固定できる。

### FR-035 — AIによる補助を提供する（P2）

AIは利用者の許可がある場合に、曖昧な要件の質問、モデル下書き、Rule式候補、シナリオ・実装候補を提案する。

**受け入れ条件:**

- AI提案は適用前に差分として表示される。
- 事実として与えられた入力、AI推測、未解決質問を区別する。
- AIは承認なしにモデル、コード、GitHubへ書き込まない。
- モデル変更案には対応するテスト案を添える。
- テナント設定によりAI機能を完全に無効化できる。

## 6. チーム機能・商用機能

### FR-040 — メンバーと権限を管理する（P1）

- Owner / Editor / Viewerを持つ。
- プロジェクト閲覧・編集権限を制御する。
- メンバー追加・削除と権限変更を監査記録に残す。

### FR-041 — Git連携を行う（P1）

- モデルファイルを指定リポジトリ・ブランチへPull Requestとして提案する。
- 生成コードは顧客のCI上で生成する方式を基本とする。
- トークンは最小権限で保管し、いつでも解除できる。

### FR-042 — プラン制限・課金を管理する（P1）

- Free / Teamなどのプランと上限を明示する。
- 既存データのエクスポートをプラン変更や解約で妨げない。
- 課金、請求、税処理は提供地域と事業形態を確認してから実装する。
