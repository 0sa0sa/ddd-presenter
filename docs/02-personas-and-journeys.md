# 02. Personas and User Journeys

## 1. ペルソナ

### A. DDDを導入したいテックリード

- チーム: Python中心のバックエンドチーム。
- 状況: 設計ルールをレビューで伝えているが、コード上の実装方法が人によって異なる。
- 望むこと: EntityやInvariantの書き方を揃え、生成差分をレビューしたい。
- 不安: 生成器に主導権を取られ、独自要件に合わないコードが大量に出ること。
- 成功: モデル変更がコード・テストの差分として見え、手書きロジックが安全に残る。

### B. ドメイン実装を担当するPythonエンジニア

- 状況: 業務知識を聞きながら、Entity、VO、状態遷移、例外、Use Caseを実装する。
- 望むこと: Pythonに不慣れなメンバーも理解できる型とコメント、実行できるテストの土台。
- 不安: YAML DSL自体が独自言語となり、Pythonより難しくなること。
- 成功: モデルが読みやすく、生成コードを通常のpytest / mypy / IDEで扱える。

### C. ドメインエキスパート

- 状況: 開発チームと条件や例外を口頭・文書で共有する。
- 望むこと: 業務語彙や処理順を図で確認し、誤解を早期に見つけたい。
- 制約: Python構文や内部アーキテクチャの知識は必須にしたくない。
- 成功: 自分が知る条件が名前付きで表示され、業務シナリオとして合意できる。

### D. 受託開発・複数案件の開発責任者

- 状況: 案件ごとに設計とコード品質を再現したい。
- 望むこと: テンプレートやモデルを複製し、チームで共通の生成ポリシーを使う。
- 成功: 初期実装を速め、顧客固有ルールと共通基盤を区別できる。

## 2. Jobs-to-be-Done

- 「業務ルールを話し合った直後に、名前付きのルールとして記録したい」
- 「この状態変更がどのガードと不変条件を適用しているか知りたい」
- 「ユースケースの順序とトランザクション境界を人が読める形にしたい」
- 「モデル変更がコードへ与える影響を、生成前に差分で確認したい」
- 「既存コードベースに段階的に導入し、必要な箇所だけ生成したい」

## 3. 主要ジャーニー: 新しいドメイン機能を作る

1. 利用者がワークスペースとプロジェクトを作る。
2. プロジェクトのPython設定、生成方式、型チェック方針を選ぶ。
3. bounded contextを作り、用語と責務を定義する。
4. Entity / Value Object / Aggregateとフィールド制約を追加する。
5. InvariantとStateGuardに業務語彙で名前を付け、条件と失敗時のDomain Errorを指定する。
6. 状態遷移とDomain Eventを定義する。
7. Use CaseのCommand、読み込み、Domain操作、保存、イベント公開などの順序をつなぐ。
8. Given-When-Thenシナリオを追加する。
9. モデル診断で未解決参照、循環依存、条件の型誤り、イベント未定義を修正する。
10. 生成前のプレビューでファイル一覧、追加・変更・削除を確認する。
11. ローカルCLIでコードとpytestテストを生成し、型チェック・テストを実行する。
12. 生成結果をGitでレビューし、未対応の複雑処理を手書き拡張ポイントに実装する。

## 4. 主要ジャーニー: 既存モデルを変更する

1. Git上のYAMLモデルを取り込む、またはWebで最新モデルを開く。
2. 変更するルールやフィールドを修正する。
3. 影響分析で参照するUse Case、テスト、生成ファイルを確認する。
4. 自動生成テストと既存テストの追加・変更・削除を確認する。
5. 差分を確認して生成し、既存の手書きファイルに触れないことを確認する。
6. CIで同じCLIバージョンによる生成差分とテストを検証する。

## 5. 主要ジャーニー: ドメインレビューをする

1. ドメインエキスパートと開発者が図のモードでContext、Aggregate、Use Caseを確認する。
2. 各ルールを選ぶと条件・評価タイミング・違反時の例外・使用箇所を表示する。
3. シナリオをGiven-When-Thenでレビューする。
4. 意味に合意したモデル変更をGit上でレビュー・承認する。

## 6. 操作上の基本方針

- 図、フォーム、テキストDSLは同じモデルを編集するビューとする。
- 図形の配置と意味上の関係を区別し、図の位置変更でモデルの意味を変えない。
- エラーはファイル、要素、フィールド、原因、修正案を示す。
- モデルの各要素から生成ファイル、コード位置、テストへ移動できる。
- 破壊的変更は生成後でなく生成前に警告し、影響範囲を表示する。
