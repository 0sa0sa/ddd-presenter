# 11. ディスカバリーボードと編集支援の使い方

モデルを書く前の「何を集約にするか・どこでコンテキストを切るか」を決める段階から、YAML を書く段階、全体をアーキテクチャ図で確かめて操作する段階（§9）までを支援する機能のガイド。設計上の決定は [docs/09](09-implementation-decisions.md) §5 を参照。

## 1. ディスカバリーボード（EventStorming）

プロジェクトの「ディスカバリー」タブ。モデルに Aggregate がまだないプロジェクトはこのタブから開く。

### 進め方の目安

1. **ドメインイベントを並べる** — 業務で起きた出来事を過去形で、時系列に左から右へ（「招待が送られた」「招待が受諾された」）。細かさより数を優先する。
2. **コマンドとアクターを置く** — そのイベントを起こす操作（「招待を受諾する」）と、実行する人（「スタッフ候補」）。アクター → コマンド → イベントを矢印でつなぐ。
3. **ポリシーを書く** — 「〜されたら〜する」自動の反応。イベント → ポリシー → コマンドとつなぐ（反映するとモデルのポリシーになる）。
4. **論点を残す** — 疑問・対立はホットスポット（赤）に書いて先に進む。
5. **集約を決める** — コマンドを受けて、一度の変更で必ず守るルールを持つまとまり。コマンドから集約へ矢印を引き、守るルールをルール付箋で書く。
6. **コンテキストの境界を引く** — 付箋を範囲選択して「コンテキストで囲む」。言葉の意味が変わる所・担当が変わる所・ポリシーでつながる所が候補。
7. **モデルに反映する** — 「モデルに反映…」で英字の名前を決め、差分を確認して YAML に入れる。

### 操作

| 操作 | 方法 |
|---|---|
| 付箋を置く | ツールバーの種類をクリック（画面中央に置く）／キャンバスをダブルクリック（その場所に置く） |
| テキストを編集 | 付箋をダブルクリック、または選んで Enter。⌘/Ctrl+Enter で確定、Esc で取消 |
| 矢印を引く | 付箋にマウスを乗せると出る端の丸からドラッグ |
| 範囲選択・移動 | 空いている所をドラッグで範囲選択／ホイールか右ドラッグで画面を移動 |
| 削除・複製・元に戻す | Delete／⌘D／⌘Z（やり直しは ⌘⇧Z） |
| フレーム | フレームを動かすと中の付箋も一緒に動く。付箋の所属は位置で決まる |

変更は自動で保存される。ほかの人の変更は数秒で画面に反映される。同時に保存して衝突したときは、どちらを残すかを選ぶダイアログが出る。

### 整理の補助（右パネル）

- **ヒント** — EventStorming でよくある抜けを指摘する（過去形でないイベント、結果のイベントがないコマンド、誰が実行するか分からないコマンド、きっかけのイベントや実行するコマンドがないポリシー、コマンドを受けない集約、ルールのない集約、未解決の論点、どのコンテキストにも入っていない付箋、大きすぎるコンテキスト）。クリックすると該当の付箋へ移動する。
- **集約の候補** — 矢印と配置から、同じものを変更するコマンド・イベントのまとまりを示す。集約がまだないまとまりには、文中に共通する名詞から名前の案を出し、「集約として置く」で付箋を置ける。**候補は提案であり、集約にするか・どこで分けるかはチームが決める。**
- **コンテキスト** — フレームごとの集約・コマンド・イベントの数と、フレームをまたぐ「イベント → ポリシー → コマンド」の連携（コンテキストマップの候補）。

### モデルへの反映で起きること

| ボード | モデル |
|---|---|
| フレーム | Bounded context（フレームがなければ `Core`） |
| 集約 | Aggregate（`id: UUID` を識別子にする） |
| 集約につながるコマンド | Operation と、それを呼ぶ Use case（load → invoke → save → publish_after_commit）。「このコマンドで集約を新しく作る」にチェックしたものは Factory と create の Use case |
| コマンドから出るイベント | Operation の emits |
| アクター | Use case の actor |
| イベント → ポリシー → コマンド | コマンドのコンテキストのポリシー（`when` はイベント、`run` はそのコマンドの Use case、`args` は Use case の必須入力をイベントから埋める）。名前は付箋のコード名（snake_case）、なければ `<コマンド>_on_<イベント>` |
| フレームをまたぐポリシー | `when: <上流>.<イベント>` と、コンテキストマップの関係（`relationships`。既定 `customer_supplier`）。関係が既にあれば `events` にイベントを足す |
| ルール付箋 | Aggregate の説明に `TODO ルール: …` として残す（条件式は推測しない） |
| 日本語のラベル | 用語集（ラベル → 英字名） |
| ホットスポット・リードモデル・外部システム | 反映しない（理由を表示） |

既存のモデルがある場合は、足りない要素だけを追加し、既にある要素は変更しない。推測が必要なもの（フィールドのある既存 Aggregate へのファクトリ追加、引数が必要な既存操作の Use case、Use case の入力をイベントから決められないポリシー、`separate_ways` の関係をまたぐポリシーなど）は理由を付けて「手で書くもの」として示す。ポリシーの入力は、同じ名前のイベントのフィールドか `<集約>_id ← event.id` で埋められるときだけ反映する（例: 「招待が受諾された」→ 同じ招待を操作するコマンドなら `invitation_id: event.id`）。反映した内容は YAML エディタに未保存の変更として入るので、フィールド・状態変更・Rule・シナリオを書き足してから保存する。

## 2. YAML エディタの補完（Web・VS Code 共通）

同じ言語サービス（`packages/core/src/language.ts`）が、Web のエディタと VS Code 拡張の両方で動く。

| 機能 | Web | VS Code |
|---|---|---|
| 補完 | 入力中に自動、Ctrl+Space | 入力中に自動、Ctrl+Space |
| 説明の表示 | マウスを乗せる | マウスを乗せる |
| 定義へ移動 | ⌘/Ctrl+クリック、F12 | ⌘/Ctrl+クリック、F12 |
| 名前の一括変更 | F2（型と State guard） | F2（型と State guard） |
| 診断 | 下の一覧と行の印 | 問題パネルと波線 |

補完が出る場所の例:

- キー — その場所で書けるキーと意味（既に書いたキーは出さない）
- `type:` — 組み込み型、Enum、Value Object、同じ Aggregate の Entity、`List[`、`Ref[`
- `error:` / `raises:` / `not_found:` / `fail:` — Domain error
- `publish_after_commit:` — そのコンテキストのイベント
- `operation:` — 読み込んだ変数の Aggregate の操作。`save:` / `target:` — それまでに読み込んだ変数
- ポリシーの `when:` — そのコンテキストのイベント、続いて別のコンテキストのイベント（`Context.Event`。イベント契約に載っているものを先に）。`run:` — そのコンテキストの Use case。`args` — キーに Use case の入力、値に `event.` のフィールド・`clock.now`・`ids.new`
- `relationships` — `upstream:` / `downstream:` にコンテキスト、`pattern:` に関係の種類（説明つき）、`events:` に上流のイベント
- Rule 式 — フィールド・引数・関数。`status == ` の後や `changes` の Enum フィールドでは Enum 値を先頭に出す。`require:` では State guard。Use case の条件では入力・変数・`変数.ガード`・`clock.now`・`ids.new`・Extension point
- シナリオのデータ — Enum フィールドの値

### VS Code 拡張のインストール

```sh
bun run build:vscode      # packages/vscode/ddd-presenter-0.1.0.vsix を作る
code --install-extension packages/vscode/ddd-presenter-0.1.0.vsix
```

`*.ddd.yaml` を開くと有効になる（ネットワークには接続しない）。

## 3. 予測と提案（Tab で書き進める）

GitHub Copilot のように、次に書きそうな内容を半透明で先に表示し、Tab で確定できる。予測には2種類ある。

- **ローカルの予測**（常に使える・送信なし）: モデルの構造から決まる続き。`packages/core/src/assist.ts`。
- **AI の予測**（ワークスペースで有効にしたときだけ）: AI がモデル全体を読んで続きを書く。ワークスペースのオーナーが「設定」タブで、使う AI を選んで有効にする。オンのあいだ、予測・提案のたびにモデル（YAML）やボードの内容が選んだ AI に送られる。切り替えは監査ログに残る。

### 使える AI

サーバーは起動時に、使える AI を見つけて「設定」タブの選択肢に出す。

| AI | 条件 | 送信先 |
|---|---|---|
| Claude API | サーバーに `ANTHROPIC_API_KEY`（または `ANTHROPIC_AUTH_TOKEN`）を設定 | Anthropic |
| Claude Code（ローカルCLI） | サーバーのマシンで `claude` が使え、ログイン済み | Claude Code 経由で Anthropic |
| Codex CLI（ローカル） | サーバーのマシンで `codex` が使え、ログイン済み | Codex 経由で OpenAI |

- ローカルの CLI は、API キーなしで、手元の Claude / ChatGPT のサブスクリプションで使える。サーバーを動かしているマシンのログインを使うので、チームで共有するサーバーでは、そのアカウントの利用枠を全員で使うことになる。
- CLI はコーディングエージェントとしてではなく、文章の生成だけに使う。Claude Code は `--tools=`（ツールなし）・MCP なし・ユーザー設定とフックなし・独自のシステムプロンプトで、Codex は read-only のサンドボックスでシェル・ブラウザ・プラグインを無効にして動かす。どちらも空の一時ディレクトリで起動する。
- 1回の予測は数秒〜数十秒かかる（CLI の起動を含む）。入力を続けると、途中の呼び出しは止める。同時に動かす CLI は最大2つ。
- Claude Code の予測は既定で速いモデル（`haiku`）、提案は CLI の既定モデルを使う。

| 環境変数 | 意味 |
|---|---|
| `DDD_AI` | `off` で AI を使わない。`claude-code,codex` のように書くと、その AI だけを選択肢に出す |
| `DDD_AI_MODEL` / `DDD_AI_INLINE_MODEL` | Claude API・Claude Code のモデル（提案用 / 予測用） |
| `DDD_AI_CODEX_MODEL` / `DDD_AI_CODEX_INLINE_MODEL` | Codex のモデル |
| `DDD_CLAUDE_BIN` / `DDD_CODEX_BIN` | CLI の場所（PATH にない場合） |

### YAML エディタ

| 操作 | キー |
|---|---|
| 予測を確定 | Tab（補完の一覧が出ているときは補完が優先） |
| 予測を消す | Esc |
| 今すぐ予測する | ⌥\ / Alt+\ |

予測は行末で、入力が止まってから表示される（ローカルは約0.35秒後、AI は約0.9秒後で、届いたらローカルの予測と入れ替わる）。ローカルの予測が出る場所:

| カーソルの場所 | 予測される内容 |
|---|---|
| `operations:` の新しい項目 | まだどの操作も遷移させていない状態へ進む操作（例: `revoke`）。State guard・`changes`・既存の命名に合わせたイベント（`InvitationRevoked`）つき |
| `emits:` の後 | 操作名から作ったイベントと、運ぶフィールド（識別子と引数） |
| `changes:` の後 | 操作名から推測した、状態フィールドの次の値（`revoke` → `status: revoked`） |
| `require:` の後 | その操作に合う、いちばん単純な State guard |
| `state_guards:` の新しい項目 | まだない状態のガード（`is_pending` など）とエラー |
| `scenarios:` の新しい項目 | ガードに違反して失敗するケース（Invariant に先に弾かれない状態を選ぶ）か、成功するケース。値は `user@example.com` のように型と名前から具体的に作る |
| `use_cases:` の新しい項目 | どの Use case からも呼ばれていない操作を呼ぶ手順 |
| `errors:` の新しい項目 | 参照されているのに定義されていない Domain error |

どの予測も、確定したときにエラーが増えないものだけを表示する（AI の予測もサーバーで同じ確認をする）。

### 集約への提案（差分で確認）

アウトラインや図で Aggregate を選ぶと、右の詳細に「提案してもらう」が出る。「次の操作」「ルール」「シナリオ」「イベントの内容」を押すと、提案が差分で表示される。適用するまでモデルは変わらず、適用しても未保存の変更として入る。提案には次の3つが分けて書かれる。

- モデルからわかっていること（事実）
- 推測（チームで確認すること）
- ドメインエキスパートへの質問

AI が有効なら、自由な指示（「招待の再送を追加して。再送は3回まで」など）でも提案させられる。AI の提案が検証エラーになった場合は、エラーを伝えて一度だけ直させる。

### ディスカバリーボード

付箋を置くと、その並びから次に置きそうな付箋が半透明（点線の枠）で表示される。クリックまたは Tab で本物の付箋と矢印になり、× か Esc で消える。ツールバーの「予測を表示」で表示を止められる。

- コマンドの右に、それが成功したときのイベント（「招待を受諾する」→「招待が受諾された」）
- イベントの左に、それを起こすコマンド（「招待が取り消された」→「招待を取り消す」）
- 集約につながっていないコマンドのまとまりに、集約の案

選択中の付箋（なければ最後に置いた付箋）に関係する予測だけを表示する。AI が有効なら「AI に付箋を提案してもらう」で、足りなさそうなアクター・ポリシー・ホットスポットなどもまとめて提案される（紫の枠）。

## 4. ワークショップの進行（ボード右パネル「進行」）

EventStorming のワークショップを、進行役がいなくても順に進められるようにする。どの段階にいるかとタイマーはボードに保存され、ボードを開いている全員に同じものが見える。

| # | 段階 | すること | 自動のチェック |
|---|---|---|---|
| 1 | 出来事を出し合う（15分） | ドメインイベントを思いつくだけ書く | 10枚以上ある・過去形で書かれている |
| 2 | 時系列に並べる（20分） | 左から右へ並べ、重複をまとめ、節目の出来事（ピボタルイベント）に印を付ける | 矢印が左→右に沿っている・同じ内容の付箋がない・ピボタルイベントがある |
| 3 | 流れを説明する（30分） | コマンド・アクター・ポリシー・リードモデル・外部システムを足す | どの出来事にも原因がある・どのコマンドにも実行者かポリシーがある |
| 4 | 集約とルールを決める（30分） | 集約とルールを置く | どのコマンドも集約につながっている・ルールがある |
| 5 | 境界を引いて優先順位を決める（20分） | コンテキストの枠を引き、コア／支援／汎用に分け、論点に投票する | 枠がある・付箋が枠に入っている・分類した・投票した |
| 6 | モデルに反映する（15分） | 「モデルに反映…」で YAML にする | 集約・コマンド・イベントがモデルに結び付いている |

- 各段階に、進行役の問いかけの例と、使う付箋の種類が出る。ツールバーでは使う種類が強調され、ほかは薄くなる（置けなくはならない）。
- チェックを押すと、まだの付箋にズームする。
- **タイマー**: 段階の目安時間・5分・10分から始める。残り時間は全員に同じものが出る。
- **投票（ドット投票）**: 「投票する」を押してから付箋をクリックすると1票、Shift+クリックで取り消し。1人の票数は1〜10票で変えられる（既定3票）。票の多い順に一覧が出る。
- **ピボタルイベント**: イベントの詳細で「流れの節目になる出来事」にすると、赤い枠と縦の点線が付く。前後で言葉や担当が変わるなら、コンテキストの境界の候補。
- **スイムレーン**: ツールバーの「☰ レーン」で横の帯を足す。人・部署・プロセスごとに分けると、誰の流れかが分かりやすい。上下に動かし、高さを変えられる。
- **ホットスポットの解決**: ホットスポットの詳細で「結論が出た」にし、結論を書く。解決したものは薄く表示され、未解決の数に数えない。
- **コメント**: 付箋ごとに質問や決まったことを残せる（書いた人と日時つき）。付箋に 💬 の数が出る。
- **サブドメインの分類**: コンテキストの枠の詳細で、コア（競争力の源）・支援・汎用を選ぶ。枠と右パネルに表示される。

### AI 進行役（チャット）

ボード右パネルの「AI 進行役」で、AI がチャットで問いかけながら、上の6段階を進める。進行役がいないとき、1人で考えるとき、慣れていないチームの最初のワークショップに使う。ワークスペースで AI を有効にしたときだけ使える（§3）。

1. 「進行を始める」を押す。何を作りたいかを入力欄に書いて「送信」してから始めてもよい（例: 「個人用の Todo アプリ。追加して、完了にして、期限を過ぎたら知らせたい」）。
2. 進行役は、いまの段階の目的と自動のチェック（上の表）、ヒント（§1）を見て、1回に1〜2個の質問をする。空のボードなら、作りたい業務と最初に考える流れを尋ねる。
3. 答えると、答えから作った付箋の案が付く。案はボードに半透明で表示され、「ボードに追加」でまとめて置く。「ボードで選ぶ」は1枚ずつクリックで追加し、要らないものを × で消す。「アクター → コマンド → イベント」のように続けて提案された付箋は、追加すると矢印でつながる。
4. 返答の候補のボタンを押すと、その文で答えられる。メッセージを書かずに「続けて」を押すと、いまのボードを見て次の問いかけをする（付箋を手で動かしたり足したりしたあとに使う）。
5. 段階のチェックが済むと、進行役が次の段階を提案する。「『時系列に並べる』へ進む」を押すと段階が変わる（「進行」タブと同じ。全員の画面で変わる）。

進行役の決まりごと:

- ボードは変えない。付箋の追加と段階の切り替えは、人がボタンを押したときだけ行う。
- 業務の事実を作らない。分からないこと・意見が分かれることは、ホットスポットの付箋として提案して先に進む。画面や DB の話に先走ったときも、ホットスポットに残して段階に戻す。
- 話題にした付箋は「話題の付箋を表示」でボード上に強調できる。

会話はこのブラウザに、ボードごとに保存される（最新の80件。ほかの人の画面には出ない）。共有されるのは段階とタイマー（ボードに保存）と、追加した付箋。全員で使うときは、進行役の画面を共有して1か所から入力する。「最初から」で会話を消せる（付箋は消えない）。1回の返答には数秒〜数十秒かかり、「止める」で中断できる。

## 5. ボードとモデルの同期（ボード右パネル「モデル」）

ボード → モデルは「モデルに反映…」、モデル → ボードはこのタブで行う。付箋はモデルでの名前（英字）で要素と結び付いている。いまのエディタの内容（未保存の変更を含む）と比べる。

| 表示 | 意味 | 操作 |
|---|---|---|
| モデルから消えた・名前が変わった付箋 | 付箋のモデルでの名前がモデルにない | 名前が変わった先の候補（結び付いていない同じ種類の要素）を押すと付け替わる。「結び付きを外す」で未反映の付箋に戻す |
| モデルにだけある要素 | YAML で足したコンテキスト・集約・操作・イベントがボードにない | 「置く」「すべてボードに置く」。コンテキストの枠の中に「コマンド → 集約」と、コマンドが出すイベントを並べる（枠がなければ作る）|
| サブドメインの分類が違うコンテキスト | 枠の分類（コア・支援・汎用）とモデルの `subdomain` が違う | 「ボードをモデルに合わせる」か「モデルをボードに合わせる」（YAML に未保存の変更として入る）|
| まだモデルにない付箋 | モデルでの名前がない集約・コマンド・イベント・ポリシー | 「モデルに反映…」|

- ポリシーは「イベント → ポリシー → コマンド」の並びで結び付く。モデルにだけあるポリシーを置くと、ポリシーが実行する Use case のコマンドの左に置かれ、イベントとコマンドへの矢印が引かれる。
- 枠の分類は「モデルに反映…」でも、分類のないコンテキストに `subdomain` として入る（すでに分類があるコンテキストは変えない）。モデルから枠を作るときは、モデルの分類が付く。
- YAML エディタの F2 や右の詳細で型（集約・イベントなど）の名前を変えると、**モデルを保存したとき**に、すべてのボードで古い名前を指していた付箋が新しい名前に付け替わる（保存しなかった変更はボードに反映しない）。
- 手で名前を書き換えた場合は、このタブに「名前が変わった付箋」として出るので、候補を押して付け替える。

## 6. 複数のボードと画像での保存

- ボードの上のタブで、プロジェクトに複数のボードを持てる（ワークショップごと・業務の流れごとなど。最大20）。「＋ ボード」で追加、タブのダブルクリックで名前を変更、選んでいるタブの × で削除（「メイン」は消せない）。モデルへの反映と同期は、開いているボードに対して行う。
- ツールバーの「書き出し」で、ボードを SVG（拡大しても鮮明）・PNG（チャットや資料に貼る）・draw.io（.drawio。draw.io で開いて編集できる）で保存できる。ボード名と日付が入り、付箋・矢印・枠（サブドメインつき）・レーン・投票が描かれる。

## 7. draw.io（diagrams.net）の図を読み込む

draw.io で描いた EventStorming の図やホワイトボードの清書を、ディスカバリーボードに付箋として取り込める。ツールバーの「draw.io を読み込む」でファイルを選ぶ。

- 読めるファイル: `.drawio` / `.xml`（圧縮されたページも可）と、図を含めて書き出した `.drawio.svg`（書き出すときに「図のコピーを含める」を選ぶ）。複数ページのファイルは、ダイアログでページを選ぶ。
- 図形は**塗りの色**で付箋の種類を決める。ダイアログに色ごとの数と例が出るので、推測（EventStorming のよくある色: 橙＝イベント、青＝コマンド、黄＝集約／小さい黄＝アクター、薄紫＝ポリシー、緑＝リードモデル、桃＝外部システム、赤＝ホットスポット、灰＝ルール）を確かめ、違えば色ごとに付箋の種類を選び直す。「読み込まない」も選べる。
- 白一色の図は文字から推測する（「〜された」はイベント、「〜する」はコマンド、「？」で終わればホットスポット）。
- 形で決まるもの: 人型（umlActor）はアクター、コンテナ・スイムレーン・他の図形を囲む大きな点線（または塗りなし）の四角はコンテキストの枠。画像や文字のない図形は読み込まない。グループやコンテナの中の図形は正しい位置に置く。
- 矢印は、両端が付箋になった図形のときだけ付箋の間の矢印になる（ラベルも引き継ぐ）。
- 読み込み先は「新しいボードとして」（ページ名がボード名になる）か「いまのボードに追加」（既存の付箋の右側に置く。⌘Z で取り消せる）。
- このツールから書き出した `.drawio` は、同じ色・位置・枠・矢印で読み戻せる。

## 8. 変更が消えないための仕組み

- **ボードの同時編集**: ほかの人が先にボードを保存していたら、付箋・枠・矢印・レーンごとに合わせて保存する（3方向マージ）。別々の付箋への変更・追加・削除はすべて残る。同じ付箋への投票とコメントは、両方の分を合わせる。同じ付箋を同時に別の内容に変えたときだけ、上に案内が出る（自分の変更を残し、「相手の版に戻す」でその付箋だけ相手の内容にできる）。
- **ボードの保存の失敗**: 通信やサーバーの問題で保存できないと、ツールバーに「保存できませんでした…自動で再試行します」と出て、間隔を空けながら（最長30秒）保存し直す。「今すぐ再試行」も押せる。未保存の変更があるうちにページを閉じようとすると警告が出る。ボードから別のタブや画面へ移るときは、自動保存を待たずにその場で保存する。
- **モデルの下書き**: 保存していない YAML の変更は、このブラウザに一時的に残る。画面を移ったりページを閉じたりして戻ってくると「前回の未保存の変更があります」と出て、復元するか破棄するかを選べる。その間にほかの人が新しい版を保存していた場合は、そのことが案内に出て、復元して保存すると差分を確認してからどちらを残すか選ぶ（黙って上書きしない）。

## 9. アーキテクチャ図の使い方

プロジェクトの「アーキテクチャ」タブは、モデルから導いたアーキテクチャを C4 モデルの考え方で3つのレベルに分けて描く。図はモデル（YAML）から毎回作り直すので、モデルと食い違わない。図に固有なのは配置だけで、配置はレベルごとに保存される。設計上の決定は docs/09 §23、`ddd generate` が出す同じ内容の `ARCHITECTURE.md` は docs/05 §10。

### レベルと移動

| レベル | 描くもの |
|---|---|
| システム全体 | コンテキスト（サブドメイン・`tenant` などのバッジ）、コンテキストの関係（パターンとイベント契約）、利用者（Use case の `actor`）、プラットフォームロール、外部システム（拡張ポイント） |
| コンテナ | このモデルとターゲットで生成されるもの: Web クライアント（TanStack Query）・HTTP API・セキュリティ・コンテキストごとのアプリケーションとドメイン・イベント配信・PostgreSQL（RLS・trigram）・ID プロバイダ・外部システム。線にプロトコルを書く（HTTPS JSON・SQL・JWKS・プロセス内イベント） |
| コンテキストの中身 | 集約（`tenant` / `global`）・Use case（authorize・レート制限・cross-tenant）・クエリ（trigram・ページ）・ポリシー・ポート（リポジトリ・リーダー・拡張・時計・ID・監査など）・生成されるアダプタ（HTTP ルート・インメモリ・PostgreSQL・顧客の拡張） |

- ツールバーの「システム全体」「コンテナ」とコンテキストの選択で切り替える。コンテキストやコンテナを**ダブルクリック**（またはクリックで選んで **Enter**）すると、そのコンテキストの中身に入る。上のパンくずで戻る。
- 要素や線を選ぶと右（幅が狭いときは下）のパネルに、種類・技術・説明・バッジ・関係が出る。「YAMLで開く」でモデルの該当行へ、「生成されるファイル」のリンクで生成プレビューのそのファイルへ移る（リンクは保存済みの版から生成したもの）。
- コンテキストの中身では、線が多いので、選んだ要素の線にだけラベルが出る。
- 要素をドラッグすると配置が変わり、レベルごとに保存される（意味は変わらない）。「自動配置」でそのレベルの配置を消して自動の配置に戻す。新しく増えた要素は、配置済みの要素の下に並ぶ。

### 図から操作する（編集者・所有者）

操作はどれもモデル（YAML）への**未保存の編集**になり、ステータスバーの「保存」で確定する。モデルを不正にする操作は適用されず、検証のエラー（例: ポリシーが使っているイベント契約の関係は削除できない、`separate_ways` にイベントは付けられない）がパネルやダイアログに出る。「↶ 元に戻す」は、このタブで行った操作を順に取り消す（その後に YAML を手で直していたら、YAML エディタの Ctrl/Cmd+Z を使う）。

| やりたいこと | 操作 |
|---|---|
| コンテキストを足す | 「＋ コンテキスト」で名前（PascalCase）とサブドメインを入れる |
| コンテキストをつなぐ（関係を足す） | システム全体で、上流のコンテキストの縁の点から下流のコンテキストへドラッグする。またはコンテキストを選び、パネルの「下流のコンテキストへ関係を追加」で選ぶ（キーボードだけでもできる）。ダイアログでパターンとイベント契約（上流が発生させるイベントから選ぶ）を決める |
| 関係を直す・消す | 線を選び、パネルの「編集…」「削除」 |
| サブドメインを決める | コンテキストを選び、パネルの「サブドメイン」 |
| 外部システムを足す | 「＋ 外部システム」（またはパネル）で、問い合わせるコンテキスト・名前（snake_case）・説明・戻り値の型を入れる。モデルには拡張ポイントとして入り、生成では顧客が実装する雛形になる |
| 生成の設定 | 「生成・セキュリティ設定」で、生成ターゲット（Python / TypeScript）と HTTP API（`generation.typescript.api`）を切り替える |
| セキュリティ | 同じダイアログで、`security` がなければ「セキュリティを追加」（ロール1つと Bearer JWT を入れ、authorize のない Use case・集約・クエリに `authenticated`、ポリシーが実行する Use case に `internal` を付ける）。あれば、PostgreSQL の行レベルセキュリティ（`tenancy.rls`、マルチテナントのとき）と既定のレート制限を変える |

閲覧者は、図を見る・選ぶ・書き出すことだけができる（配置も変えられない）。

### 書き出し

「書き出し」で、いま表示しているレベルを SVG・PNG・draw.io（.drawio。draw.io で編集できる）・Mermaid（.mmd）で保存する。「Mermaid をコピー」でクリップボードに入れ、README や Issue に貼れる（GitHub は `mermaid` コードブロックをそのまま図にする）。SVG・PNG・draw.io は画面の配置のまま書き出す。

## 10. 複数ファイル形式との行き来

モデルのタブの下にある「複数ファイル形式…」から、モデルを `.proto` / `.domain` / `.flow` / `.scenarios.yaml` / `ddd.yaml` に分けた形式（docs/10 §12）で扱える。

- **見る・編集する**: ファイルの名前を選んで中身を見る。編集者・所有者はその場で書き換えられ、入力のたびにモデル全体を検証して、誤りをファイル名と行で出す（変えたファイルに ●、エラーのあるファイルに ✕）。「編集をモデルに反映」で YAML に変換してエディタに入れる（保存はまだしない）。
- **書き出す**: 「ZIP で書き出す」でまとめてダウンロードする（編集中ならその内容）。モデルにエラーがあるときは書き出せない。
- **読み込む**（編集者・所有者）: ZIP、複数のファイル、またはフォルダを選ぶ。読み込んだ結果の診断（ファイル名と行）が出る。「エディタに取り込む」で YAML に変換してエディタに入れる。保存はまだされないので、差分を確かめてから保存する。`.proto` / `.domain` / `.flow` の説明でないコメントは YAML には残らない。

保存されるのは YAML。複数ファイル形式のファイルを手元に置いて編集し続けるときは、CLI（`ddd validate <フォルダ>`）と VS Code 拡張機能を使う。

## 11. プロダクトマネージャーのレビュー（「レビュー」タブ・`ddd review`）

保存されたモデルから「はい／いいえ」で答える文を作り、プロダクトマネージャー（PM）に業務として正しいかを最終判断してもらう。文は、モデルが Entity・Value Object・参照・組織・ロール・状態をどう結び付けているかを、業務の言葉で一つずつ言い切ったもの。

| 分類 | 例 |
|---|---|
| 組織（テナント）の分離 | 「ある組織のユーザーは、別の組織のスタッフ候補への招待を見られる。」「上位の組織の管理者は、配下の組織のメンバーやデータをすべて見られる。」 |
| 誰が何をできるか | 「staff は『revoke_invitation』を実行できる。」「candidate は、本人の email がスタッフ候補への招待の email と同じときだけ『招待を受諾する』を実行できる。」 |
| 状態の移り変わり | 「『accepted』の招待に対して、『招待を取り消す』ができる。」「一度『revoked』になった招待は、その後ほかの状態に変わらない。」 |
| つながり | 「Order は、必ず 1 つの Customer に紐づく。」「同じ email を持つ招待が 2 つ以上あってもよい。」「OrderLine を 1 つも持たない Order がある。」 |
| 守るべきルール・入力する情報・自動で起きること | Invariant と State guard の説明、必須かどうかと長さ、ポリシー、反応する処理のないイベント、2 回届いた依頼の扱い |

- **答え方**: 文が業務として正しければ「はい」、違えば「いいえ」。もう一度押すと取り消す。迷うものはメモを残す。回答は誰がいつ答えたかと一緒にプロジェクトに保存され、メンバー全員に見える（閲覧者は見るだけ）。
- **モデルの答えは隠す**: 既定ではモデルの答えを表示しない（先に見ると、それに引っぱられるため）。「モデルの答えを表示」で根拠と一緒に出る。
- **直すもの**: モデルと違う答えには、いまのモデル・直し方・場所（「モデルで見る」で YAML の該当行へ）が出る。モデルに置き場所のないこと（組織の親子関係、データの削除、複数の組織への所属）には「モデルにない」と答える質問があり、「はい」と答えるとモデル（または DSL）に足すべきものとして数える。
- **書き出し**: 「質問票（Markdown）」は回答欄つきの表（モデルの答えなし）、「結果（Markdown）」は回答と直すものの一覧。
- 質問の ID は要素の名前から作るので、ほかの所を編集しても回答は残る。要素の名前を変えると新しい質問になり、前の回答は「使われなくなった回答」に出る。

CLI では `ddd review [model]` が同じ質問票を Markdown で出す。`--key` でモデルの答えと根拠つき、`--template` で回答を書き込む YAML（`"質問の ID": yes / no`）、`--answers <file>` で回答を読み、直すものを一覧にする（直すものがあれば終了コード 1）。

## 12. フロー図のレビューと編集（「レビュー」タブ → 「フロー図」・`ddd review --flows`）

`.flow` に書いた手順（Use case・クエリ・ポリシー）を図にして、人に順番・止まる所・どこで何をするかを確かめてもらう。図はモデルから作るので、図と手順がずれることはない。「レビュー」タブの上の切り替えで「フロー図」を選ぶ。

| 図 | 何が描かれるか |
|---|---|
| イベントのつながり | 人（黄）が始める Use case（青）、それが発行するイベント（橙）、反応するポリシー（紫）、ポリシーが動かす Use case。コンテキストをまたいでつながる。点線の枠は反応するものがないイベント |
| Use case ごとのシーケンス図 | 左から、呼ぶ人、HTTP / Connect API、セキュリティ（認証・レート制限）、そのコンテキストのアプリケーション、集約、PostgreSQL、イベント配信、ほかのコンテキストのアプリケーション。上から順に、読み込み・権限の確認（`allow_if`）・操作（説明つき）・ガード・保存・イベントの発行・反応するポリシーが並ぶ |
| クエリごとのシーケンス図 | 検索の条件（組織での絞り込み・`where`・あいまい検索）、並び順、1 ページの件数、返す項目 |

- **止まる所**: `if` は「分岐」の枠、条件に当てはまるときだけ起きることは「場合」の枠になる。失敗（見つからない・権限がない・ガードを満たさない・保存の競合・`fail`）は ✕ の矢印で、呼んだ側に返る。条件は、できるものは日本語にする（例: 「本人の email がスタッフ候補への招待の email と同じ」でない）。
- **どこで何をするか**: 図の列は `ddd generate` が作る部品（docs/09 §23 のコンテナ）に合わせる。API を生成しない設定では、呼ぶ人がアプリケーションを直接呼ぶ。ポリシーだけが動かす Use case は「イベント配信」から始まる。
- **答え方**: 図ごとに「この流れで合っている？」に「はい／いいえ」で答え、違う所をメモに書く。回答は質問（§11）と同じく保存され、質問の一覧にも「手順の流れ（フロー図）」として出る（「図で見る」で図に移る）。回答は見た図に結び付く: 図が変わると（手順・説明・エラーの文言など）新しい質問になり、前の回答は「使われなくなった回答」に回る。
- **フローを直す（編集者・所有者）**: 「フローを直す」で、その Use case・クエリの `.flow` のブロックが開く（イベントのつながり図では、ポリシーを押すと開く）。`.flow` の書き方（docs/10 §12.4）で書き換え、「適用」（Ctrl/Cmd + Enter）でモデル（YAML）に入る。図はすぐに描き直される。保存するまではほかの人に見えず、図への回答もできない（保存したモデルの図にだけ答えられる）。
  - 書き方の誤りや、モデルとして通らないこと（知らない変数・エラー名、保存していない変更など）は、ブロックの中の行に出て、適用されない。ブロックの名前と種類、入力の名前は変えられない（`.proto` 側で決まるため）。
  - YAML に戻すのは、そのブロックが決めるキー（Use case の `steps` と `authorize`、クエリの `from`・`where`・`search`・`order_by`・`page`・`returns`・`authorize`、ポリシーの全体）のうち、意味が変わったものだけ。ほかの所のコメントや並びはそのまま残る。書き換えた `steps` の中の YAML のコメントは消える。
- **書き出し**: 「Mermaid をコピー」はその図を Mermaid の文で、「フロー図（Markdown）」はすべての図を Mermaid つきの Markdown で（GitHub・Notion などでそのまま図になる）。

CLI では `ddd review [model] --flows` が同じ Markdown を出す（`--format json` で図のデータ）。

## 13. 証明（「レビュー」タブ → 「証明（Z3）」・`ddd verify`）

保存したモデルの Aggregate について、Factory・Operation ごとに「ガード（`require`）を満たしたあとで、Invariant や制約に断られることがあるか」を Z3 で調べる（docs/09 §29）。「レビュー」タブの上の切り替えで「証明（Z3）」を選ぶ。初めての版は数秒かかる（サーバーが版ごとに覚える）。

| 結果 | 意味 |
|---|---|
| 証明 | どんな状態・引数でも断られない。リストを含むものは「リストは N 個まで調べた」と出る（モデルがリストの大きさと比べる数まで） |
| 反例 | 断られる具体的な値。前の状態（関係するフィールドだけ）と引数を出す。Factory から数手でたどり着ける場合は「手順: open → add_line → …」も出る |
| 不明 | 時間切れ。Z3 が決められなかった |

- **反例への答え**: 反例ごとに「この場合に断るのは正しい？」に「はい／いいえ」で答える。同じ質問が「質問（はい／いいえ）」の一覧にも「断られる場合（Z3 の反例）」として出る（「反例を見る」でこのタブに来る）。「いいえ」なら、断らずに済むように changes を直すか、`require` にガードを足して先に理由を示す。その前の状態が業務で起きないなら、それを Invariant として足すと反例が消える。手順が付かない反例は、たどり着けない状態からのもの（Invariant が足りない）かもしれない。
- **シナリオとして足す（編集者・所有者）**: 反例をその Aggregate のシナリオ（前の状態・操作・`raises`）としてモデルに足す。生成するテストが、この場合にそのエラーになることを確かめるようになる（未保存の変更として入る。足すとモデルにエラーが出る場合は足さない）。
- **成功しない操作**: どんな状態・引数でもガードかチェックに断られる操作は、上に赤で出る（`never-succeeds` の警告）。
- **前提**: 「前提」を開くと、証明が成り立つ条件（前の状態は Invariant を満たす、文字列の中身は見ない、リストの上限、Use case は対象外など）が出る。「証明された」はこの前提の中での話。
- **書き出し**: 「証明（Markdown）」で結果と前提を Markdown に。

CLI では `ddd verify [model]` が同じ結果を Markdown（`--format json` でデータ）で出す。

- `--smt2 <dir>`: 調べた問いをそれぞれ単独の SMT-LIB 2 のスクリプトとして書き出す（`z3 file.smt2` など別のソルバーで確かめ直せる）。
- `--depth n`: 反例の手順を Factory から何手まで探すか（既定 2、0 で探さない）。
- `--lean <dir>`: リストの上限つきで証明したものを Lean 4 の定理として書き出す（`lean Proofs/<コンテキスト>.lean` で型検査できる。証明は `sorry`）。`--prove` を付けると、Claude Code に証明を書かせて Lean で確かめる（`--lean-cmd` で lean の場所。`sorry`・公理・`native_decide` を使う証明は受け付けず、最後に `#print axioms` で確かめる）。証明できたものは結果に「Lean で証明（リストの長さに上限なし）」と出る。
- 成功しない操作があれば終了コード 1（`--strict` で反例があっても 1）。
- `ddd review --proofs` で、質問票に反例の質問を足す。

### 振る舞いの変化（AI の提案・`ddd changes`）

AI の提案ダイアログ（Inspector の「提案」）は、差分の上に「振る舞いの変化」を出す。テキストではなく意味で比べ、検査を緩める変更（▲）を先頭に出す。

| ▲ 検査を緩める変更 | 例 |
|---|---|
| ルールを消す・変える | Invariant を消す、式を変える、確かめる時（construct / transition）を減らす、State guard の式を変える |
| ガードを外す | Operation・Factory の `require` から外す、Use case の手順の `fail` を減らす |
| テストを消す | シナリオを消す、`raises` を変える・消す |
| 受け付ける値を広げる | 制約を緩める（`min` を下げる、`max_length` を上げる、`pattern` を消す）、必須を外す |
| 権限を広げる | `public` にする、ロール・権限を足す、`allow_if` を変える、security・テナントの分離・RLS を外す |
| 状態をまたぐ | ある操作が、前はできなかった状態でもできるようになる |

ほかに、質問へのモデルの答えが変わるもの、できなくなる操作、新しく加わるルールも出る（▲ なし）。AI に「このテストを通して」と頼むと、検査そのものを緩めてしまうことがある。▲ が出たら、それが意図した変更か確かめてから適用する。

CLI では `ddd changes <before> [model]` が、別の版のモデル（ファイルかディレクトリ。例: main ブランチから取り出したもの）からの変化を同じ形で出す。`--check` で、検査を緩める変更があれば終了コード 1（CI で使う）。

### プロパティテスト（`generation.property_tests: true`）

モデルの `generation` に `property_tests: true` を書くと、Aggregate ごとにランダムな Factory・Operation の列を流すテストを生成する（Python は Hypothesis、TypeScript は fast-check）。呼び出しは成功するか、モデルがその呼び出しに宣言したエラーを出すかのどちらかでなければならず、それ以外の例外で失敗する（失敗した手順は短く縮めて表示される）。Python は開発用の依存に `hypothesis` を、TypeScript は `fast-check` を足す（新しく作る package.json には入る）。`pytest --hypothesis-show-statistics` で、どの操作がどれだけ成功・失敗したかが見られる。
