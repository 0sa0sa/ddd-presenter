# 07. Business Model and Market Validation

## 1. 事業仮説

**仮説:** DDDを採用したいPython開発チームは、業務ルールの整理とテスト可能なドメインコードの生成、再生成の安全性に対して、チーム単位の継続課金を支払う。

この仮説は未検証。技術的な実現可能性や競合製品の存在は、支払い意向や市場規模を証明しない。

## 2. 顧客課題の優先仮説

優先度の高い順に検証する。

1. Invariantや状態条件が複数箇所へ重複し、変更漏れが起きる。
2. DDDの定型実装に時間がかかり、規約がチーム内で揃わない。
3. ドメイン変更がコード・テストへ与える影響を把握しにくい。
4. 非エンジニアを含むレビューで、図とコードの間に断絶がある。
5. 生成コードを安全に再生成し、手書き実装を保持できる手段がない。

## 3. 競合・代替の初期調査

### 初期ポジショニング案

「DDD図を描くツール」ではなく、「ドメインルールを実行可能なソース仕様として管理し、レビューできるPythonコードへ継続的に変換するツール」として検証する。

### 差別化仮説

- Invariant / StateGuard / 状態遷移を明示的にサポートする。
- モデルと生成テスト、Use Case手順、コード上の利用箇所を相互に追跡する。
- YAMLとローカルCLIにより、顧客のGit・CI・Python環境の中で動く。
- 手書き拡張を上書きせず、変更影響を生成前に見せる。
- Pythonに不慣れな利用者へ用語解説・図解・生成コードの説明を行う。

## 4. 収益モデル仮説

価格は未決定。最初に支払い意向を確認してから上限とプランを設計する。

### 試すプラン構成

- **Solo:** 個人のモデル作成、CLI、基本コード生成。無料または低価格で導入障壁を測る。
- **Team:** 共有Workspace、共同レビュー、GitHub連携、変更履歴、チームテンプレート。
- **Enterprise:** SSO、SCIM、監査ログ、プライベート実行、専用サポート、組織ポリシー。

価格単位候補: 開発者席数、アクティブプロジェクト数、またはチーム単位。モデル数課金は顧客の設計・分割を歪める懸念があるため、避ける候補として検証する。

## 5. 顧客開発計画

### Discovery interview（初期10〜15名）

聞く質問:

- 最近、業務ルール変更でどの実装・テストを直したか。
- 条件式の重複、例外の不一致、生成コードの上書きで困った事例はあるか。
- 現在の設計資料とコードは何を正として同期しているか。
- Entity / VO / Use Caseの定型実装にどれくらい時間がかかるか。
- 新しい開発ツールを導入する決裁者、セキュリティ条件、購買期間は何か。
- 1つのbounded contextを持ち込むPoCに参加し、予算を払う可能性はあるか。

仮説を誘導しない。実際の過去作業と購入行動を聞き、「便利そう」という反応だけを需要証拠にしない。

### Concierge PoC（3〜5チーム）

- 顧客が提供可能な小さな業務Contextを一つ選ぶ。
- 既存実装、モデル作成時間、生成後修正量、テスト変更量を記録する。
- 同じモデルを手作業の型・テストと比較し、品質レビューする。
- 2〜4週間使用して再生成・変更を最低一度試す。
- 終了時に継続利用条件と具体的な支払い金額を確認する。

### 継続判断の目安

- 3社以上が自分のリポジトリへ生成結果を採用する。
- 2社以上が毎週継続利用する。
- 少なくとも2社が具体的な有料プランまたは契約条件を検討する。
- 生成物の修正・保守コストが、定型実装の削減価値を恒常的に上回らない。
- チームが「モデルを更新する」習慣を実際に継続する。

## 6. 販売・導入経路仮説

- 技術記事とサンプルrepoで、Invariant / StateGuardからコード・テストを生成する体験を提示する。
- Python/DDDコミュニティ、開発者向けイベント、受託会社への直接PoC。
- 既存Pythonアプリの一つのbounded contextへ導入するガイドを提供する。
- 導入時に独自DB移行や全面書き換えを必須にしない。
- 顧客の成功例は許可を得たうえで、業務ルールと生成差分の匿名化ケースとして公開する。
