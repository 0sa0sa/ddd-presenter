# 01. Product Brief

## 1. 概要

DDD Presenterは、ドメインモデルからPythonのドメインコードと検証用テストを生成する、モデル駆動開発サービスである。EntityやValue Objectの型定義だけでなく、命名された不変条件、状態ガード、状態遷移、ユースケースの手順、Given-When-Thenシナリオを一つのモデルで扱う。

Web上で図とフォームを使ってモデルを編集し、プロジェクト内のYAMLモデルファイルとして書き出す。ローカルCLIがモデルを検証し、決定的にコードとテストを生成する。顧客は生成物を通常のPythonプロジェクトで使い、変更をGitでレビューする。

## 2. 顧客の課題

DDDを実践しようとすると、チームは次の作業を何度も手作業で行う。

- Entity、Value Object、Aggregate、Command、Eventの型とファイルを作る。
- 同じ業務条件をコンストラクタ、状態変更メソッド、Use Case、テストに重複して書く。
- 条件式に名前を付け、どの業務ルールがどこで適用されるかを維持する。
- ドメインモデル変更後に、型、テスト、API境界、ドキュメントの追随漏れを見つける。
- DDDの用語やパターンに不慣れな開発者へ、既存コードの意図を説明する。

コード生成だけでは、業務上の正しさは得られない。価値は、業務上の判断を明示されたモデルにし、検証・生成・レビューの基点を一つにすることにある。

## 3. ビジョン

人が業務の意味、ルール、処理順、期待する結果に集中し、繰り返しの型定義やルール適用の配線をツールに任せる。生成コードをブラックボックスにせず、開発者が読んで修正できる通常のソースとして提供する。

## 4. 価値提案

> ドメインルールに名前を付けて一度定義すれば、適用箇所・テスト・コード生成で一貫して使える。

想定する顧客価値:

1. 同じ条件の複製を減らし、ルールの変更漏れを見つけやすくする。
2. Entity / Value Object / Aggregateの定型実装を減らす。
3. ルールごとの単体テストとユースケースごとの受け入れテストをモデルから作る。
4. DDDの設計判断を図・用語・コードの間で追跡できる。
5. コード生成の差分をレビューでき、生成後も通常の開発手順で運用できる。

## 5. 初期ターゲット

**主要顧客:** Pythonで業務システムやSaaSを開発する5〜30人程度の開発チーム。複数の業務ルールを持つ既存アプリ、または新規の業務系プロダクトを担当し、型安全性とテストを重視している。

**初期利用者:** DDDを推進するテックリード、バックエンドエンジニア、ドメインエキスパートと要件を整理するエンジニア。

**後続候補:** 受託開発会社、社内開発基盤チーム、業務アプリ向けフレームワーク提供者、Python以外のDDDチーム。

## 6. 成功指標

初期の成功は登録数で測らず、モデルから生成されたコードを実プロジェクトが採用したかで測る。

| 指標 | 初期目標の仮説 | 測定方法 |
|---|---:|---|
| 初回価値到達時間 | 30分以内 | サンプルモデルから生成コード・テストを得るまで |
| 生成結果の採用 | PoC参加チームの半数以上 | 実リポジトリへ生成コードをコミットしたか |
| 再生成の安全性 | 主要変更シナリオで手書き拡張を破壊しない | モデル変更→再生成→差分レビューを実施 |
| ルール追跡性 | 主要ルールをモデルから利用箇所とテストへ辿れる | 要件レビュー時の追跡確認 |
| 継続利用意向 | 3チーム以上が次の機能でも使用希望 | 4週間のPoC後インタビュー |

数値は市場実証前の仮説であり、顧客とのPoCで更新する。

## 7. 初期版で対象とする範囲

- 一つのbounded context内のドメインモデル。
- Value Object、Entity、Aggregate Root、Domain Error。
- Field制約、Invariant、StateGuard、状態遷移。
- Command、Domain Event、Repository等のPort。
- ユースケースの入力、順序、条件分岐、トランザクション境界の宣言。
- Given-When-Thenシナリオと生成テスト。
- Pythonのドメイン層・アプリケーション層の生成、差分確認、再生成。
- YAMLモデルのエクスポート、ローカルCLIでの検証・生成。

## 8. 初期版の対象外

- あらゆる業種の業務ロジックを自然言語だけで完全自動実装すること。
- DB、クラウド、認証、決済、監視環境の本番設定を自動確定すること。
- 任意の既存コードを完全にモデルへ逆変換すること。
- ORMやWebフレームワークを固定した巨大な実行時ライブラリ。
- Event Sourcing、分散Saga、複雑な分散トランザクションの完全実装。
- 初回リリースでの多言語同時サポート。
- AIがレビューなしでモデルや顧客コードを変更・送信すること。

## 9. プロダクト原則

1. **モデルが意図、コードが実行物:** 顧客はモデルも生成コードも所有する。
2. **生成結果を読める:** 出力は慣用的で、特殊ランタイムを必須にしない。
3. **生成は再現可能:** 同じモデルと同じジェネレータ版から同じ結果を作る。
4. **再生成は安全:** 生成物と手書き拡張の境界を明示する。
5. **規則の意味を隠さない:** 条件、例外、評価タイミング、状態変更を表示する。
6. **不明点を捏造しない:** AIを追加しても、推測と確定したモデル判断を分ける。
7. **段階導入できる:** 既存Pythonプロジェクトへドメイン単位で導入できる。
