# 08. Roadmap, Risks, and Open Decisions

## 1. 段階的ロードマップ

ロードマップは日程約束ではなく、次段階へ進むための証拠で定義する。

### Phase 0 — 課題検証とCLIプロトタイプ

**実施内容:**

- 5〜10件の顧客インタビュー。
- PythonでInvariant / StateGuard / 状態遷移 / Use Caseを含むYAML試作。
- CleaningStaffInvitation等のサンプルからPythonコードとpytestを生成。
- 手書き拡張を保った状態で再生成できるか確認。

**Exit criteria:**

- 3チーム以上が実データ相当のContextを持ち込みたい。
- 生成物がレビュー後に既存プロジェクトへコミットされる。
- モデル変更時の再生成が手作業より確実・説明可能と評価される。

### Phase 1 — MVP: ローカルモデル駆動生成

**実施内容:**

- schema付きYAML、パーサ、型検証、Rule検証。
- Entity、Value Object、Aggregate、Domain Error、Invariant、StateGuard生成。
- 状態遷移、Command / Event / Port、Use Case順序の生成。
- Given-When-Thenからpytestを生成。
- CLIのvalidate / generate / diff / version。
- Golden testsとサンプルアプリ。

**Exit criteria:**

- 新規・更新・削除差分が説明できる。
- 生成物が型検査とテストを通り、手書き拡張を壊さない。
- 2つ以上の実チームで継続利用される。

### Phase 2 — Web編集・チームレビュー

**実施内容:**

- 図とフォームでContext、Aggregate、Use Case、Ruleを編集。
- 診断、影響分析、ルール利用箇所、シナリオ表示。
- Workspace、権限、履歴、モデルdiff。
- ローカルCLIはWebアカウントなしでも基本利用を続けられる。

**Exit criteria:**

- 開発者以外もモデルレビューへ参加し、レビューの手戻りが減る。
- チームがモデルとコードを同じPull Requestで更新する。

### Phase 3 — Git連携・AI支援・拡張言語

**実施内容:**

- GitHub Pull Request、CI連携、モデル・コードの差分追跡。
- AIによる質問、モデル案、シナリオ案、拡張コード候補。
- 顧客要望に基づきTypeScript / PHP / Java等の次言語を選ぶ。
- チーム課金、監査、SSOなど必要な商用機能。

**Exit criteria:**

- AI支援が手作業時間を減らし、誤った推測を増やさない。
- 有料転換と継続利用が確認できる。

## 2. 主なリスク

| リスク | 影響 | 対応 |
|---|---|---|
| 独自DSLがPythonコードより難しい | 学習負担が増え利用が止まる | YAMLを極小に保ち、図・フォームとCLIを用意。顧客がPythonで直接書く方が楽な部分を調査する。 |
| 顧客がモデルを更新せず、コードと乖離する | Source of truthが形骸化する | Git PRにモデルdiffを含める、CIで生成差分を検知する。更新習慣の形成をPoCで確認する。 |
| 生成コードが実務に合わず修正が多い | 生成器保守費が価値を上回る | 安定したExtension API、手書き拡張領域、生成後の修正量計測。 |
| 規則式が表現不足 | 顧客固有ロジックを扱えない | 型付きExtensionPointを用意し、式言語を無制限に拡張しない。頻出パターンだけ追加する。 |
| 規則式が過剰に複雑化する | 可読性と検証性が落ちる | 式の複雑度警告、名前付きRuleへの分割、例の表示を提供する。 |
| DDD自体が初期顧客に難しい | 導入・販売が遅い | チュートリアル、用語ガイド、既存Pythonアプリへの限定導入を提供する。 |
| 競合がAIコード生成へ急速に寄せる | 差別化が弱まる | 再現可能性、ルール追跡、CI、コード所有権、顧客リポジトリとの継続同期で比較する。 |
| 顧客のドメインモデルが機密 | クラウド利用を拒まれる | ローカルCLIを第一級に扱い、Webにアップロードする情報を選べるようにする。 |
| コード生成を「正しさの保証」と誤認する | 欠陥と法的・信用リスク | 生成対象・検証範囲を明示し、業務シナリオのレビューを必須にする。 |
| 複数言語を早く追加する | コスト増・出力品質のばらつき | 言語非依存IRは設計しつつ、最初は一言語で顧客価値を検証する。 |

## 3. 未決事項

次の事項は要件の仮置き。PoCで回答する。

1. 顧客がYAML DSLを自分で編集するのか、Webフォームだけを望むのか。
2. Python生成でPydanticを必須にするか、stdlib profileも必要か。
3. Entityの更新スタイルを変更可能オブジェクトにするか、不変オブジェクトの置換にするか。
4. 生成コードを一つのpackageにまとめるか、顧客のレイヤー構成を選択可能にするか。
5. Use CaseモデルでSQLトランザクション、Outbox、再試行・冪等性をどこまで宣言するか。
6. UI上のテストシナリオ編集を誰が担当するか。ドメインエキスパート向け構文が必要か。
7. SaaSが保存するモデル情報と、ローカルでのみ保持する情報の境界。
8. 価格単位、無料枠、有料導入を決める購買者と予算区分。
9. 主な市場を日本にするか、初期から英語圏も狙うか。
10. 初期のAI提供先、データ保持、顧客組織のAI利用禁止への対応。
